## Testing

- **Run all tests**: `cd mobile && npm test -- --no-coverage`
- Jest uses isolated TypeScript transpilation via its configured tsconfig so ordinary `npm test` fits a 2 GB machine. It does not perform semantic type checking: `npm run typecheck` remains a separate required check. No temporary Jest configuration is needed.
- **CI runs the suite in-band** (`npm test -- --no-coverage --ci --runInBand`, see `.github/workflows/ci.yml`); run it that way before pushing anything that touches timers or deferred `require()`s. In-band, one process outlives every suite, so a timer armed by one suite fires during a later one, and a module first required after the arming suite's teardown trips Jest's import-after-teardown guard, which sets the exit code to 1 with every test green (CI run 442 on `main`, 2026-09-14: 209 suites passed, exit 1). A multi-worker run cannot show it, since each worker's exit code is discarded. The global setup `src/__tests__/helpers/jestSetup.ts` (`setupFilesAfterEnv`) cancels `eventLogger`'s 5 s debounce timer after every suite through `cancelPendingFlushForTests`, which closed the only source that run had. The hook reaches the suite's live module registry only: a suite that calls `jest.resetModules()` or `isolateModules` after arming the timer must mock `eventLogger` or call `clearEvents()` itself. The flush also never throws past its timer (a telemetry module without an uploader is skipped, not cached), so any leak the hook misses stays a soft exit code rather than a crashed run.
- **Run a single test file**: `cd mobile && npm test -- --no-coverage --testPathPattern=<filename>`
- **Three checks need a real computer, not a phone.** `npm run typecheck` needs well over 1 GB of heap (Termux on Android aborts with a JavaScript heap OOM); `skyGeometry.test.ts` and `shopIconGeometry.test.ts` import `sharp`, which has no android-arm64 runtime (devDependency only, never bundled, and those two suites are its only consumers); and Playwright refuses Android outright, so `npm run test:e2e` cannot run there. Everything else passes under Termux. Read these three off the CI run for the same commit instead of treating them as failures.
- **A script whose stdout another process parses must `console.log` a STRING.** `console.log(<number>)` (or any non-string) goes through `util.inspect`, which adds ANSI colour whenever colour is forced, and `FORCE_COLOR` is propagated by an interactive Jest run and set by some CI runners. `gatedCheckpointCount.mjs` shipped this bug: the three gated drivers read its count into shell arithmetic, where an escape code is `syntax error: operand expected`, and the resulting Jest diff reads `Expected: "0" Received: "0"` because the terminal renders the escapes invisibly. `gatedTooling.test.ts` now pins the output under `FORCE_COLOR=1`.
- **CI also verifies the daily leaderboard cohort stamp** (`node scripts/tools/updateDailyBoardVersion.mjs --check`, the "Puzzle delivery policy and daily cohort" step). The hash covers the five standard banks, `dictionary.ts`, the vocabulary policy files, `puzzleBank.ts`, `bankDeliveryPolicy.ts`, `dailyChallenge.ts`, `dateUtils.ts` AND `constants/gameBalance.ts`, so editing any of them, a tuning constant included, requires re-running the tool without `--check` and committing `src/services/dailyBoardVersion.ts` (a new stamp only partitions the leaderboard; it never changes a board). The second launch-readiness merge went red on exactly this after the economy tuning and the daily-cohort recording touched two hashed files.
- **Browser journeys**: `cd mobile && npm run test:e2e` (Playwright over the Expo web build in `mobile/e2e`; point `WORDSHIFT_CHROMIUM` at the installed Chromium). `e2e/onboarding.spec.ts` is the ONLY journey that starts from an EMPTY save (no `wordshift_onboarding_step` or intro flags seeded) and drives cold_open_puzzle -> home_empty -> fox_invited -> pit_intro -> pit_offering -> unlock_explained -> complete plus the cold-open Skip confirm; never seed onboarding state in its beforeEach, and it pins the automatic invite effect rather than the den-chip tap.
- **Run tests for changed files only**: `cd mobile && npm test -- --no-coverage --changedSince=main`
- Do NOT use `npx jest` directly — it does not find the local install and triggers a full remote download + deprecated dependency warnings every time. Always use `npm test` which routes through the locally installed jest.
- `npm install` IS allowed in this environment. Fresh containers may start without `node_modules`; run `cd mobile && npm install` (or `npm ci`) once at the start of a session before running tests/typecheck/lint. Prefer `npm ci` when `package-lock.json` is present and unchanged.
- The suite is expected green; the latest recorded CI totals and native validation limits live in [Current build](docs/CURRENT_BUILD.md). **Prefer running the relevant test file(s)** unless a required gate or concrete remaining risk calls for the full suite. Documentation edits alone do not need a full gameplay test run.

## Dialogue Readability Pass (2026-09-02)

> Historical implementation snapshot. Preserve its evidence; use the current reference and active topic sections for present behavior.

A player report that lines needed re-reading turned out to be measurable, and the cause was register and delivery rather than vocabulary (the corpus scores Flesch 80.6 / grade 5.2 — the WORDS were never hard).

**What was wrong.** The contraction rate was **14%** (1,139 expanded forms against 189 contractions: "I have" 248 times, "it is" 207, "I am" 101) where natural speech runs 65-80%, so every animal read like written prose. Comma density was **1.02 per sentence**, double conversational, giving clause chains the reader has to hold in memory. And the paginator's 420-character budget almost never fired against a corpus averaging 273 characters a line, so **92% of dialogue arrived as ONE ~8-line block** behind a six-second typewriter.

**Register (phase-aware, and the gate is now a narrative device).** Contractions were applied to **phases 0-3 only**; the Phase 4-5 liturgy keeps its expanded forms. So the corpus went from a flat 14% to **93-96% at phases 0-3 and 19% at phase 4**: the animals audibly stop using contractions at the reveal, which makes the register itself part of the turn. Sentences over 28 words are split at a coordinating seam, never leaving a stub under 7 words. Every line, id, count, image and cross-animal echo is preserved — this was a rhythm pass, not a rewrite. Toolkit in the session scratchpad; the transform skipped any string whose phase it could not attribute (519 of 3,209).

**One grammar rule worth keeping:** English forbids a contracted auxiliary in stranded position — "We are." is grammatical, "We're." is not, while NEGATIVE contractions are fine there ("I don't."). 35 stranded auxiliaries were expanded back after the pass. Any future contraction pass must re-apply that rule.

**Delivery.** `DIALOGUE_PAGE_CHAR_BUDGET` 420 -> **200** (8.4 rendered lines per page -> 4.8; pages of 7+ lines 80% -> 13%; reveal 5.6s -> 3.0s). The typewriter cadence is phase-aware (`getDialogueRevealCharMs`): **15 ms/char through Phase 1** (`DIALOGUE_REVEAL_CHAR_MS_BRIGHT`, the 3.0 s page above) and **22 ms from Phase 2** (`DIALOGUE_REVEAL_CHAR_MS`, where the slowness is the point). The bubble has always been tap-to-complete; the hook now exposes `revealSkipHint` (phase-aware copy from `getDialogueRevealSkipHint`, device-local key `wordshift_reveal_skip_hint_seen`), non-null only while the first reveal this device ever shows is in progress, for the host to render faintly under the bubble. `components/home/DialogueBody` renders **one sentence per block** with a 7dp gap so the eye has a landing point per thought; the splitter (`services/dialogueText.splitIntoSentences`) is presentation-only and **lossless** — re-joining with one space reproduces the input, including on a growing typewriter PREFIX (pinned by `dialogueBody.test.ts`), which matters because the dialogue flow compares `dialogueText` against choice prompts by equality and the gallery records the unsplit line. The bubble also steps up from the 15/25 chrome body to **16/27**, being the one long-form reading surface in the game.

### Scene Dialogue Register Pass (2026-09-22)

The 2026-09-02 pass repaired the house corpus and never reached the SCENE

Three rules now govern every scene pool, pinned by `sceneDialogueRegister.test.ts`:

1. **A line's band is the phase its scene is DELIVERED at, never the file it
   lives in.** Story gates: cup/old_mark 0; echo/witness/plum 1;
   supper/plan/shelter 2; record 3; seeds/promise/returned/council 4;
   after/reply 5. File-level contraction rates are averages of a correct band
   and a broken one, and chasing them damages finished work: `phaseEvents` reads
   6% only because it is ~95% narration, and `dialogueChoices` reads 16% only
   because its phase-4 callbacks are correctly at 0%. **Never "raise a file to
   78%".**
2. **Narration never contracts, at any phase.** The narrator is the fixed
   baseline the residents' phase-4 turn is measured against; contract it at 0-3
   and stop at 4 and the reader cannot tell whether the residents changed or the
   book did. That covers every `narrator(...)` call and `memory:` string in
   storySpine, the `prompt`/`convergence` stage directions in dialogueChoices,
   and essentially all of phaseEvents. A narrator line that reads badly is fixed
   by promoting a real subject over an existential opener, never by register.
3. **The player contracts at every phase, 4 and 5 included.** The player never
   joined the liturgy. This covers `speaker: 'player'` lines and every option
   `label`.

Residents are **0%** from the reveal on: not "few", zero. The shipped phase-4
house corpus is 0 contractions against 312 expanded forms, and phase-5
post-revelation plus Tending is 0 against 248, so a spine that contracts while
Ember speaks liturgy at her own door in the same session is worse than either
choice made consistently. Phases 0-3 sit at 82% of all sites, which is 100% of
the CONTRACTIBLE ones: the remainder are stranded positive auxiliaries ("safer
than it is."), quoted written text ("I am afraid", whose own sentence counts
three words) and "this is" / "on it is", which have no spoken contraction.
Stranded NEGATIVES are legal and are the preferred fix ("It isn't.").

## Narrative Vision

**The core conceit**: The player's words sustain an unnamed presence. The house grows into a place that can receive it. Ember owes the player an explanation for the invitation; the other residents discover and interpret its cost through their own concerns. Affection can be real while preservation through correcting change or dissent is unacceptable. Do not flatten the residents into an omniscient conspiracy; the story implementation document defines the current canon.

**The tone shift must be gradual and earned.** The game should feel genuinely delightful for the first 25+ puzzles. Players should *like* these animals. The betrayal of that warmth is the entire point. When Fox says "The fire grows cold... but something else burns," it should land because the player remembers when Fox just wanted to tell them about cozy blankets.

**Everything reflects the transition:**
- **Puzzle words**: Shift from FUN/SPARK/TIGER → VOID/DOOM/ABYSS/RITUAL
- **Background visuals**: Bright candy purple → near-black with crimson accents
- **Floating particles**: Sparkles and stars → dim, dying embers
- **Victory text**: "PERFECT!" → "WHY DOES IT MATTER?" (plus ritual echo showing completed word chain)
- **Words offered counter**: Simple stat → "N words offered to the arrangement"
- **Move messages**: "Delicious!" → "The void accepts."
- **Confetti**: Vibrant rainbow → muted, dark colors
- **Hints**: "Move 'R' — think WARM!" → "If it matters, 'R' — see VOID."
- **Home screen**: Sunny day, happy clouds → storm sky, shadow figure looming
- **Animal sprites**: Cute idle poses → robed cult figures
- **Letter tiles**: Bouncy, fast wobble → heavy, ponderous movement with trailing glow
- **Shadow figure**: Invisible (Phase 0-2) → faint silhouette (Phase 3, opacity 0.18) → full looming presence with crimson eyes (Phase 4, 0.5) → settled (Phase 5, 0.35). `ShadowFigure` in HouseWorld.tsx renders `shadow_figure.png` behind the house with a slow breathing loop (native driver, reduced-motion aware)
- **Sound**: a 60-file SFX pack (warm additive-synth chimes with a rising combo ladder, a full dark mirror set from Phase 3, a serene Phase-5 peace tier for the most frequent sounds, warm/dark ceremony swells banded by target phase, a bespoke finale arrival cue) plus twelve authored music beds, one per phase for the house world (home, menus and the Offering Pit) and one per phase for the board, that descend with the story and settle after the arrival

**Key narrative rules:**
1. Never break the fourth wall. The animals don't know they're in a game.
2. The darkness should feel *earned*, not sudden. Each phase is a gradual shift.
3. Phase 4 is unsettling without making the animals interchangeable villains or certain believers. Preserve each resident's knowledge, uncertainty and accountability.
4. The player should feel complicit. "You solved the puzzle. You brought us closer."
5. Visual changes should slightly precede dialogue revelations — the player should *feel* something is off before they're told.
6. The shadow_figure.png entity is never named, never explained. It just *is*.
7. **Never reveal the phase system to the player.** No "Phase 2/5" labels, no progress bars toward phase transitions. The player should experience the shift organically through visuals, dialogue, and tone — never through a UI label telling them what stage they're in.

**Phase narrative arc:**
- **Phase 0 (Bright Days)**: Pure joy. Cute animals, candy colors, fun words. The trap is set.
- **Phase 1 (Curious Thoughts)**: Animals start wondering about the nature of things. Subtle philosophical undertones.
- **Phase 2 (Deeper Questions)**: Isolation creeps in. Animals question reality, impermanence. Words shift toward emptiness. The background noticeably darkens.
- **Phase 3 (Growing Shadows)**: Overt dread. Animals speak of endings, purpose, something approaching. The puzzle screen feels cold. Victory feels hollow.
- **Phase 4 (The Horizon)**: The cult is revealed. Animals speak of "the arrangement," "the pattern," "what comes through." Robed sprites. Storm sky. The shadow figure appears. Every puzzle solved is explicitly framed as part of the summoning.
- **Phase 5 (Post-Revelation)**: After the authored finale and arrival. The shadow has settled, but that does not settle every relationship. The chosen boundary remains visible; anger, hope, uncertainty and quiet are valid responses. Victory text: "The pattern continues."

## Game Mechanics

### Core Puzzle Loop
1. Player sees a chain of words (3-5 rows depending on difficulty)
2. Pick a letter from current word — word shrinks by 1 letter
3. Drop letter into next word — word grows by 1 letter
4. Both resulting words must be valid English words
5. Progress through all rows to win

**Drag z-order (contract):** the dragged tile is a floating copy rendered IN PLACE inside `DraggableTile`, so it escapes its row only if that row out-ranks its siblings — and paint order among rows is decided by their OUTERMOST elements. The drag lift therefore lives on Row's board-serve entrance wrapper (`serveWrapperDragging`, zIndex + a matching `elevation` for Android), never on an inner wrapper. Pinned by `puzzleFeelContracts.test.ts`.

**Move feedback (game feel):** a valid move plays a catch bounce + star burst with phase-weighted escalated haptics (`hapticMoveCommit(phase, dragDrop)` in haptics.ts: the crisp drag-heavy/tap-medium hit through phase 2, a delayed 110ms soft after-strike at phases 3-4, a single soft medium at phase 5; rides the haptics toggle only, never reducedMotion) and `soundValidMove()`; an **invalid drop** plays `hapticError()` + `soundInvalidMove()` + the target-row error shake (so rejection is felt at the hand, not just shown on the board — `App.tsx` `handleSlotPress` result-`null` path). **Intra-puzzle escalation:** consecutive clean moves on a board ramp the move message via `getComboMoveMessage(streak, phase)` (phase-aware, tiered at streak 2/3/4+); the streak (`cleanMoveStreakRef` in `usePuzzleGame`) resets on an invalid attempt, undo, reverse-midpoint, or new board. **Double-shift `drop1`** (half a move, no `formedWord`) gets a soft "click into place" (`hapticSelection` + `soundTap` + catch bounce), reserving the star-burst celebration for completed words. A drag released **off any row** (Y-bounds reject) now gives feedback — `hapticSelection()` + a phase-aware `getDragMissMessage(phase)` — instead of silently vanishing. **Tap-path arrival**: a tap-committed move plays an arrival settle on the moved tile (`arrivalMoveId`/`arrivalDirection` from `usePuzzleGame` → LetterTile scale/translate spring, phase-aware, reduced-motion aware); drag keeps its own collapse feedback, and autosave restore never replays an arrival. **Cross-row flight (the "flying ghost", audit F1, shipped 2026-08-31)**: the same tap commit also flies a ghost copy of the moved tile from the source tile's position into the landing slot — `ArrivalMark` carries optional flight endpoints (`flightChar`/`sourceRowIndex`/`sourceLetterIndex`/`sourceWordLength`/`targetWordLength`, absent on drag/drop1/undo/restore), and App resolves them to window coords (X analytic via `standardLetterCenterOffset` × boardScale; Y measured from the registered row nodes, stable across a commit) and renders `components/puzzle/FlyingTileGhost` (real LetterTile chrome, native driver, `TILE_FLIGHT_MS` 260ms with a `TILE_FLIGHT_LIFT_DP` bow, fades into the settle as it lands). Reduced-motion/low-tier devices skip the flight; the settle is their feedback. **Inactive tiles acknowledge taps** (pre-launch fix): tiles with no action available — completed rows, future rows, and the target row before a letter is selected — mount a feedback-only touchable instead of bare content (`onInactivePress`, threaded App → Row → LetterTile on non-source rows only). A tap fires exactly two things: `hapticSelection()` (App's `handleInactiveTilePress`, stable identity, haptic-only) and a subtle native-driver scale pulse on the tile (dip to 0.94 over ~70ms, spring back; skipped under reducedMotion while the haptic survives). No message, no sound, ZERO game-state effects; the active-row locked shake+message and the inter-slot pulse paths always take precedence, drag is untouched, and the touchable deliberately carries no accessibility role (screen readers are never promised an action). Pinned by `puzzleFeelContracts.test.ts`.

### Word Preview Mechanic
When a letter is selected, ghost previews show what word would form at each slot position. **Validity GRADING is difficulty-gated (v1.3.0 verb redesign)**: `previewValidityVisible` in `usePuzzleGame.ts` is true ONLY on EASY (any variant except blind) and in the double_shift variant at any difficulty (its intermediate non-word state needs the guidance). When visible: valid words green with a "✓ " prefix, invalid red/dimmed with "✗ " (never color alone); a slot shows ✓ only when **both** resulting words are valid (the preview ANDs source-word validity). When hidden (MEDIUM+ standard/reverse/speed, the daily, shared-challenge boards): the ghost word renders in one neutral dimmed ink with no ✓/✗ and no valid/invalid styling — the player judges the word, which is where the skill now lives (pre-redesign, 78-83% of steps had exactly one legal move and the UI graded it for free). `isValid` is still computed internally (look-ahead/blind judgment/snapping need it); the flag controls PRESENTATION only. Screen readers announce the formed word always, the verdict only when grading is shown (no a11y leak). The drag valid-slot snapping tell follows the same rule; hidden-validity boards snap to the geometrically nearest slot. **Preview-grading transition** (`resolvePreviewGradingMode` in `usePuzzleGame.ts` → `PreviewGradingMode` = `'graded' | 'neutral' | 'hidden'`, exposed as `previewGradingMode`): validity is fully graded on EVERY board (any difficulty) until `PREVIEW_GRADING_FULL_LIMIT` (12) total puzzles are solved (so the tutorial's ✓/✗ teaching never hands off cold to ungraded MEDIUM on the first free board). From puzzle 12 on, the otherwise-ungraded boards (MEDIUM+ standard/reverse/speed, daily, shared-challenge) go permanently **neutral** — the marks step back for good. The transition is **one-way**: `previewValidityVisible = previewGradingMode === 'graded'`, so a neutral board never shows the ✓/✗ and an invalid attempt does NOT bring them back (the old 'rescue' tier that resurrected grading after a mistake was removed — it read as a glitch). A one-time in-world graduation beat (`getPreviewGraduationTitle`/`getPreviewGraduationMessage`/`getPreviewGraduationConfirm`, key `wordshift_preview_graduation_seen_v2`, device-local) fires on the FIRST genuinely ungraded board, so the player is always told when the marks step back (closes the old silent-stop gap). It is delivered as an **UNMISSABLE blocking cottage card** (the `showGameAlert` host covers the board until the player acknowledges it) rather than the original fading toast — a "the rules just changed" moment must not race the board-start line or blink past unread (App.tsx gates it on `previewGradingMode === 'neutral'` so a hidden-preview rescue board can't consume it early). The flag commits on **acknowledgment** (the card's button), never at decision time, and the key is **versioned (`_v2`)** because the original toast delivery marked the old key seen before showing and the post-phase-transition moment routinely ate the toast — observed on-device: checks went neutral with no message, beat burned invisibly; the rename grants every such device one guaranteed showing of the card. Previews are suppressed ENTIRELY (`'hidden'`) only in **Blind Offering**. **No spacing after the first ceremony, by owner decision:** for an engaged new player the phase-1 pit ceremony lands on win 12 (`MIN_PUZZLES_FOR_PHASE[1]`) and the graduation card opens on board 13. A one-board deferral once existed (`notePhaseCeremonyAcknowledged`/`consumePreviewGraduationDeferral`); it was removed on 2026-09-19 (`9e3e82d`) so the card appears when the graded previews first disappear, and the owner confirmed on 2026-09-22 that no gap is wanted. Do not reintroduce it.

Player-selected from the setup menu. Persisted as preferred variant.

- **Reverse Shift** (unlock: 10 puzzles — moved from 8 pre-launch so the reverse intro waits two boards past the daily unlock (8) and the mandatory first harvest (win 9) instead of stacking on that one-time-beat cluster; `puzzleVariety.test.ts` pins the gate clears `DAILY_CHALLENGE_UNLOCK_PUZZLES + 1`): Play down then back up. The descent→ascent **midpoint** returns `reverseMidpoint: true` so App fires a celebratory `hapticSuccess()` (the return leg reads as a second act). If on-device generation can't produce a reverse-solvable puzzle and silently downgrades to standard, `startNewGame` now surfaces a phase-aware notice instead of swapping styles unannounced.
- **Double Shift** (unlock: 25 puzzles): Move 2 letters per step. 4-phase input cycle: `pick1 → drop1 → pick2 → drop2`. All words are 5 letters (W=5). Difficulty by row count: EASY=3, MEDIUM=4, MEDIUM_PLUS=5, HARD=6. 1.65x amber multiplier. The first drop (`drop1`) returns a non-null result with **no `formedWord`**, so App gives positive drop feedback (catch bounce + haptic) while skipping dread tracking — it does not fall through to the "invalid drop" error path. The `drop1` slot previews use a **look-ahead** (`canCompleteDoubleShift`): a slot shows ✓ only when some second move from there yields two valid words, so the first drop is guided, not guesswork. Stuck detection runs after each completed step via `hasAnyValidDoubleShiftMove` (the two-letter analogue of `hasAnyValidMove`), surfacing the recovery panel if the row is trapped. **Undo:** mid-step undos (before the step completes) are always free, even in Challenge mode. In **Challenge** mode, undoing a *completed* step reverts BOTH drops atomically for ONE undo charge (`handleUndo` detects the paired deltas by shared `activeRowIndexBefore`) — never a half-revert that strands the first drop or burns two charges; standard mode keeps its granular per-drop undo.
- **Speed Shift** — NOT a variant. It is the fourth composable **MODIFIER** (`speedMode`, gate `SPEED_TOGGLE_UNLOCK_PUZZLES` 55): a clock laid over whatever style is already selected, so it stacks with Challenge/Blind/Lexicon AND rides standard, reverse or double shift. `'speed'` was removed from BOTH `PuzzleVariant` and `VariantModifier` (leaving it in the modifier union would have kept every `hasVariantModifier(v,'speed')` call type-checking while silently returning false forever). It changes NO board: bank routing is untouched, so every (style × difficulty × lexicon) bank is reachable under the clock with no new bank work, and the old `rowOverride: 3` was deleted (it only ever reached the on-device generator — speed boards have been bank-served at full standard length for a long time). The clock is `getSpeedTimeLimit(difficulty, variant)` = `SPEED_TIME_LIMITS[difficulty] × SPEED_STYLE_TIME_MULTIPLIER[variant]` (standard 1.0 / reverse 1.9 / double_shift 1.6 — an EXPERT double shift is a 7-row two-letter board and the bare 44s would be unwinnable). Amber is `SPEED_AMBER_MULTIPLIER` (1.34, unchanged from the old variant rate), applied like Lexicon's inside `awardPuzzleAmber`, itemized as `speedBonus`, **reward-only — never phase progress**. Lifetime wins moved to `progress.speedWins`; `getVariantWinStats` also reads the legacy `variantWins.speed`, and **dataMigration v5** folds it forward and retires a stored `'speed'` style preference. A board autosaved by the pre-conversion build is coerced on restore (`currentVariant: 'speed'` → standard + `speedMode` on) since `puzzleSaveState` carries no schema version. Forced OFF on the finale (a countdown over a played ending breaks the beat), the daily and shared boards; speed boards are excluded from the +1-row extension (a longer chain on a shorter clock) and from house asks. Quests use a dedicated `speed_wins` type (a `variant_wins` quest keyed to a nonexistent variant would be filtered out of every draw forever). Timed run with difficulty-aware base timers (EASY 65s → HARD 48s). **Escalation ladder**: each consecutive speed win increments App-level `speedRound`, trimming the next clock by `SPEED_ESCALATION_STEP_SEC` (5s, floored at `SPEED_ESCALATION_MIN_SEC` = 30s) so a streak keeps tightening instead of letting skilled players idle. A "🔥 Round N" indicator appears under the timer once `speedRound > 0`. The ladder resets on any fresh run (Play, variant/difficulty/challenge switch, Home) and on the Time's-Up overlay exits (Try Again / Home) — **not** on time-up itself, since a rescue may continue the run; only **Next Level** continues it. The clock **pauses while the app is backgrounded** (AppState listener in `useSpeedTimer`) and while the setup menu, Rules sheet or any scheduled blocking overlay covers the board (`useSpeedTimer` composes its menu hold with `setSpeedTimerOverlayPaused`; the remaining seconds are banked, not restarted), and resumes from the saved remaining seconds after a relaunch (`speedTimeRemainingSec` in autosave; legacy `speedTimerExpireAt` still restores as a fallback). ### Late-Game Puzzle Extension (+1 row)
The mirror of the curated early ramp at the top end: once the player has solved `PUZZLE_EXTENSION_UNLOCK_PUZZLES` (70, `services/puzzleExtension.ts`), **every standard board gains one extra row**. `extendStandardPuzzle(config)` appends one canonical standard-rule move using only synchronous dictionary lookups (no re-search), so a late EASY board becomes 4 rows, MEDIUM/MEDIUM_PLUS 5, HARD 6. Applied on **both** delivery paths: bank selection filters to boards whose stored solution can be safely extended (`getCachedStandardExtension`, recycling within the extendable subset) and generation extends the served board, each with a `getGuaranteedExtendedStandardFallback(difficulty)` safety net when a specific board can't be extended. **Excluded:** reverse and double-shift (`extendStandardPuzzle` early-returns on `reverseSolution`/`isDoubleShift`), the Daily and shared-challenge boards (their own start paths never route through it), the finale board, and Unbroken Weave (extension is skipped when `requestedUnbrokenWeave`, so the one-use-per-letter eligibility set is never perturbed). Solvability is preserved by construction (the appended step is a validated real move). **Unplayed before replayed (2026-09-22):** only some boards can take the extra row (about 31 HARD, 39 EXPERT), so once every extendable board has been played, bank selection serves the unplayed remainder at its own length (`serveExtended` false) before recycling any extended board; a new board beats a replay with one more row. **Branching-preferring append (Depth Levers Pass):** the extension scan prefers a valid append whose FINAL step is not forced — `countFinalStepOutcomes` checks that 2+ distinct valid outcome words remain on the appended row (early-exits at 2), examining up to `MAX_PREFERRED_APPEND_ATTEMPTS` (40) valid appends before settling for the first valid one as fallback — so the +1 row keeps a real choice alive instead of ending every extended board on a single-move rail (sync dictionary lookups only, same order of work).

### House Asks (per-board constraint beat)
On **25%** (`HOUSE_ASK_CHANCE`) of eligible standard boards past **40** solves (`HOUSE_ASK_MIN_PUZZLES`, gameBalance — which also covers the curated early boards), the house quietly asks ONE small thing of the arrangement: a specific letter **must travel** (`'move'`) or **must be left untouched** (`'keep'`). `services/houseAsks.ts` is pure (derive/pick/evaluate, deterministic given rng); **App.tsx owns the roll, the badge, and the victory evaluation**. Both ask kinds are derived from the board's **stored solution**, so every ask is **satisfiable by construction** (replaying the stored route keeps either kind): `deriveHouseAskCandidates` collects 'move' candidates (unique solution-moved characters, step order) then 'keep' candidates (characters in a NON-final start row the solution never moves — a character whose sole presence is the final row is excluded, since final-row letters can't travel and "leave them be" would be hollow); `pickHouseAsk` draws uniformly. On multi-route boards the ask **selects between routes — which is the point** (it composes with the gated banks' guaranteed 2+ routes). Semantics are **letter-CHARACTER, never a specific tile**; `evaluateHouseAsk` judges the committed move history once, at the WON commit. **Kept:** +`HOUSE_ASK_REWARD_AMBER` (15) via `awardBonusAmber('house_ask')` (amber-only, NEVER phase progress) + a receipt-priority victory toast (`getHouseAskFulfilledMessage`). **Unkept: silence, forever** (soft-fail contract — cleared with no message; the house never scolds). Delivery: the ask rolls once per fresh board (keyed on board identity, gates read at fire time), speaks via `getHouseAskLine(phase, kind, letter)` (queued ~2.2s behind a board-start greeting rather than clobbering it), and shows a standing **🏠 badge with the letter** in the puzzle statsRow (same chrome as the variant badges; the full phase-aware ask line rides the accessibility label). **Never on:** the daily, shared-challenge boards, the finale board, Blind Offering, Unbroken Weave, non-standard variants (reverse/double/speed), during onboarding, or below the solve gate; a **restored autosave board never rolls** and a live ask does NOT survive autosave restore or leaving the puzzle screen (deliberate simplification — an interrupted board simply has no ask; suppress ref + committed-move guard in App).

### Star Rating
- **3 stars**: 0 hints, 0-1 invalid attempts
- **2 stars**: 1 hint OR 2-3 invalid attempts
- **1 star**: 2+ hints OR 4+ invalid attempts

### Unbroken Weave (Phase 5 mastery mode)

The **post-revelation apex** — a mastery pursuit that sits *beyond* the trial ladder and is reachable ONLY at the true endgame. `isUnbrokenWeaveAvailable(currentPhase, postRevelation)` (`services/unbrokenWeave.ts`) gates it to global **phase 5 AND the persisted `postRevelation` flag** (not merely a Phase-4 board that resolved to animal-phase 5). A 🧵 toggle appears in DifficultyMenu only when `showUnbrokenWeave && phase === 5 && !introMode`; `handleToggleUnbrokenWeave` in App flips `unbrokenWeaveMode` (mode is amber-only, never phase progress).

- **The one rule:** each moved letter *character* may cross the chain **exactly once** across the whole board. `usePuzzleGame` tracks a `spentLetterSet` (`isLetterSpent`/`addSpentLetter`/`removeSpentLetter` in unbrokenWeave.ts); a pick of an already-spent letter is refused with `getUnbrokenWeaveSpentLetterMessage`, and every committed move (and undo) adds/releases the letter. Look-ahead/stuck detection also filter out spent letters.
- **Board eligibility:** the mode forces a **standard** board and serves ONLY boards whose canonical solution moves all-unique single letters — `getUnbrokenWeaveEligibility(solution)` rejects `missing_solution`/`invalid_letter`/`double_letter_step`/`reused_letter`. Bank selection passes `unbrokenWeaveOnly` (filters to `isUnbrokenWeaveEligible` boards, recycles within that subset); generation validates the same way. If no eligible board can be produced (or the toggle is requested outside phase 5), `startNewGame` falls back to a normal board with `getUnbrokenWeaveUnavailableMessage` + `disableUnbrokenWeave` instead of a silent swap.
- **Undos:** free and unlimited (it runs as an ordinary standard-mode board — no challenge budget, no blind flag), and undoing releases the spent letter so the chain can be re-walked. Ordinary standard amber (no trial multiplier).
- **Reward is private mastery, not amber:** `recordUnbrokenWeaveVictory(difficulty, flawless)` advances the `UnbrokenWeaveMastery` ladder in `masteryRecords.ts` (cloud-synced under `wordshift_mastery`) — 6 ranks: **Unbroken Weave** (base) → **Thread Joined** (1 win) → **Fourfold Weave** (cleared on all 4 difficulties) → **Seamless Dark** (a flawless HARD) → **Loomkeeper** (10 flawless) → **Patternbound** (25 flawless). The VictoryModal shows the rank/title/next-objective + a rank-up line (`getUnbrokenWeaveRankUpLine`).
- **Intro & persistence:** a one-time Fox intro from HomeScreen (`hasSeenUnbrokenWeaveIntro`/`markUnbrokenWeaveIntroSeen` in amberCurrency, `getUnbrokenWeaveIntroLines`, `introContext: 'unbroken_weave_intro'`, flag `unbrokenWeaveIntroSeen` on home progress). `unbrokenWeaveMode` survives autosave in `SavedPuzzleState`. The finale board and curated early boards force it off.

### Daily Challenge
Deterministic seeded generation. **Board shape ramps across the week** (`getDailyRamp`, Mon→Sun, the Wordle/NYT pattern: Mon MEDIUM 4-letter/4-row → Tue-Wed MEDIUM_PLUS 5-letter → Thu HARD → Fri MEDIUM_PLUS breather → Sat HARD → Sun HARD 6-letter/5-row peak; deterministic by date so every player gets the same board and the leaderboard stays fair — **rewards still always count as HARD**), with one exception: a player's first **three** dailies (`EASED_DAILY_COUNT`, `isFirstDailyEasing`) are eased to the gentle MEDIUM 4-letter/4-row shape regardless of weekday (`getDailyRamp(dateStr, isFirstDaily)`), so a new player's early dailies are never a 6-letter HARD wall right as the word marks stop; eased boards stay off the shared leaderboard (`DailyPuzzleData.eased`). **The board itself is a date-seeded permutation of the shape's bank** (`selectDailyBankPuzzleForDate` in puzzleBank.ts: one position per calendar day through a Fisher-Yates order seeded by bank, size and pass), so a bank never repeats a daily until every board in it has been one; the old independent roll could repeat a Sunday board within weeks. Streak tracking with a yesterday-only **free** continuation, now backed by a **freeze mercy**: a banked daily-streak freeze (one granted every `DAILY_FREE_FREEZE_INTERVAL_DAYS`=14, capped at 1) auto-forgives a single missed day instead of nuking a long streak — `recordDailyCompletion` consumes it and returns `streakSavedByFreeze` (App surfaces a "🛡️ your daily streak held" message); `getDailyStatus` exposes `streakFreezes`. Unlocked at **8 puzzles** or Phase 1+ (`DAILY_CHALLENGE_UNLOCK_PUZZLES` in `constants/gameBalance.ts` — aligned with the close of the pit auto-collect window, so the daily lands as a challenge, not a wall). A **one-time first-daily mercy** grants +`FIRST_DAILY_BONUS_HINTS` (2) free hints when the very first daily starts (`grantFirstDailyMercy` in dailyChallenge.ts, surfaced as a toast from `App.handleStartDaily`). One-time Fox intro.

**Entry point & wiring**: A `DailyChallengeCard` (📅) sits in the **HomeScreen header**, gated by `isDailyChallengeUnlocked()` and hidden during onboarding (shows a pulsing calendar when available, a check + stars + streak badge once done; a 🌕 badge on full-moon event days via `getEventBadgeLabel`). Tapping it calls `App.handleStartDaily()` → **replay guard**: a daily already completed today re-checks the leaderboard standing instead of starting the board (for the RECORDED cohort: `getLastDailyCompletionCohort` date + board version, falling back to the session's `dailyBoardVersionRef`, never the wall-clock day and the compiled `DAILY_BOARD_VERSION`; daily victories record `dailyBoardVersion` through `VictoryInput`) (the seeded board is identical all day and pays full HARD amber + phase progress, so replays via deep link / notification tap would be pure farming) → `startDailyBoard()` → `generateDailyPuzzle()` → `puzzleActions.startDailyGame()` (a hook action that builds a standard, hint-enabled board from the seeded words **without** disturbing the player's chosen difficulty preference; takes the generator's stored `solution` so daily hints replay real steps instead of re-searching a 6-letter board on-device). App-level `isPlayingDaily` state threads through `useAutosave` (tags the save with `isPlayingDaily`/`dailyDate`; a daily save is never restored as a normal puzzle), `recordVictory(..., isDaily=true)` (rewards always count as HARD), and the VictoryModal ("Daily Challenge Complete"). On completion App calls `recordDailyCompletion()` and `checkDailyStreakMilestone()` — milestone amber is credited via `awardBonusAmber('daily_streak_milestone')` with a deferred toast — and records the standing to `dailyLadder.ts` (local history; "best this week" line in the VictoryModal). On full-moon event days the daily also pays a **+50% amber bonus** (`getEventDailyBonusAmber` → `awardBonusAmber(..., 'event_daily_bonus')` — bonus-only, never phase progress). Completions log a `daily_completed` event. `isPlayingDaily` resets on every non-daily start path (Play, variant/difficulty/challenge switch, Home, Next Level).

**Thin-board standing suppression:** the percentile is "percent of OTHER entrants beaten", so its denominator is `(total - 1)` — a lone entrant is a hard **0%** by construction and a 2-entrant board can only ever return 0% or 100%. Below `DAILY_PERCENTILE_MIN_ENTRANTS` (5, gameBalance) the sentence is suppressed the way socialProof hides a weak count: `getBeatPercentText(percentile, phase, total)` returns **`string | null`** (null below the gate; `total` is optional so a caller with no count is unchanged) and every surface substitutes `getStandingsGatheringText(phase)`. Both live in `leaderboard.ts` beside `hasMeaningfulPercentile(total)` — the single shared predicate the victory card, its accessibility label, the "Today's Standing" re-check alert and `dailyLadder`'s statistics all ask, so they cannot drift. **The RANK line is never gated** ("#1 of 1" is factually true and is the one real fact a thin board offers). `DailyLeaderboardCard` deliberately holds **no percentile prop and no fallback copy** — it renders the caller's already-judged `beatText` and nothing else, because its own hardcoded "You beat N% of players today" was what resurrected the suppressed number the first time.

## App Architecture

### Custom Hooks

**`usePuzzleGame()`** — All puzzle state: rows, selected letter, game state, hints, validation, variant handling. Key methods: `initGame()`, `startNewGame()` (guarded by a monotonic `generationIdRef`; Daily/shared starts, restore, restart, clear and unmount also invalidate an older generation, so a slow result or callback cannot replace the current board), `startDailyGame()` (Daily Challenge bypass path — standard board from seeded words, leaves difficulty pref intact), `startSharedChallengeGame(words)` (friend-challenge link path, validated), `handleLetterPress()`, `handleSlotPress()`, `handleHint()`, `handleUndo()`, `clearBoard()`. Returns `slotPreviews` for word preview mechanic. `handleHint()` also raises `hintHighlight` — the hinted tile + target slot glow on the board, reusing the tutorial-glow rendering (cleared on move/undo/new board; never restored from autosave) — and its off-solution fallback candidates filter through `isBoardSolvableFromState` (the lock-aware from-state analogue of `isChainSolvable`), so a hint never suggests a legal-but-stranding move. Tracks per-move `moveOutcomes` for the honest share grid, per-move **resonant-choice flags** (`collectDistinctOutcomeWords`/`isResonantChoice` — see Move Resonance; undo pops the flag), and raises `speedRescueSignal` from `resumeSpeedAfterRescue`. **Shared-challenge boards are amber-only**: `isSharedChallenge` threads into `recordVictory` → `awardPuzzleAmber({skipPhaseProgress: true})` (full amber, ZERO phase progress) with ritual energy forced to 0 — a friend link can never accelerate the descent; the provenance survives kill/restore via `isSharedChallenge` in `SavedPuzzleState`. After each committed move (non-double-shift), `hasAnyValidMove()` runs stuck detection and sets `isStuck` — **near-silent by product decision, with a v1.3.2 one-time mercy**: the ONLY consumer of `isStuck` is a ONE-TIME-EVER first-stuck notice in App.tsx (shows `getNoValidMovesMessage(phase)` once, behind the device-local flag `wordshift_first_stuck_seen` — deliberately NOT cloud-synced, a returning player on a new device may deserve the mercy once more); after that, stuck detection is fully silent again (no panel, no toast — discovering a dead-end and choosing Undo/Restart is part of the challenge; `appIntegration.test.ts` pins this exact contract). `getStuckPanelTitle()` remains in phaseNarrative but intentionally unused. `isStuck` resets on undo/restart/new board.

**`useGamePersistence()`** — Persistence: amber, stats, phases, streak. Key: `recordVictory()` returns VictoryData (includes `phaseTransitionPending`, `harvestedWords`, `pendingHarvest`, `firstCompletionBonus`). It enqueues ONLY the per-puzzle `amberResult.amount` into the harvest batch (the milestone/first-completion/streak-milestone windfalls are already balance-credited by `awardPuzzleAmber` — see Offering Pit Economy); `VictoryData.amberEarned`/`amberBreakdown.total` still carry the full earned receipt (queued share + windfalls) so the modal itemization sums exactly. `refreshStats()` reloads from storage. Reports phase 5 when post-revelation.

**`useVictoryFlow()`** — Victory animation: star pop-in, modal reveal, phase flash, driven by a `VictoryStage` state machine (`idle → recording → choreographing → settled`) plus `victorySpinnerVisible` so no spinner flashes during choreography. `playVictorySequence(stars)`, `skipToEnd(stars)`, `resetVictory()`. `isProcessingVictory` lock prevents double-tap.

**`useVictoryOrchestration()`** — Post-victory cascade: glitch text, narrative micro-beats, animal whispers, interjections, home nudges. Generation-guarded async callbacks. The home nudge (3+ chained wins away from home) speaks **at most once per app session** (`shouldOfferHomeNudge`, module-scope guard like the heavy-harvest nudge) from a five-line phase-aware pool; before that it replaced the 30%-gated interjection on every later win. Whispers are **frequency-gated** (exported `getWhisperChance(phase)`: 0.45 phases 0-3, 0.6 phase 4, always at phase 5 — the personalized whispers are the endgame feature); the roll happens BEFORE generation, so a skipped win also skips the gallery `recordWhisper` (a line the player never saw must not fill the archive). The interjection overlay renders with `pointerEvents="none"` so it never blocks board input.

**`useDialogueFlow()`** — Ordinary introductions, sequential regular conversations, session cooldowns, reactions, seeds/callbacks, repeating pools and durable choices. `conversationProgress.ts` selects the earliest eligible unread stable line ID and commits it only after Next on its final page. Close, backdrop dismissal and interrupted reveal leave the line unread. Opening and delivery have generation ownership; Next locks during the save and exposes retry on failure. The host receives the committed read-ID map so later amber-only progress updates cannot restore a stale conversation position. Phase-2 exhaustion and Phase-5 Tending follow eligible regular lines. Mode tutorials are acknowledged only after their final page.

**`useUnlockFlow()`** — Home unlock flow: in-world room/animal prompts, purchases, intro dialogue for new characters.

**`useOnboardingFlow()`** — Cold-open onboarding state machine: self-directed opener board → invite Fox on home → pit → home (legacy guided-puzzle steps kept for resume compatibility). Fox text/step helpers, two-step skip, pit offer-complete.

**`useDreadEffects()`** — Crimson pulse overlay + screen shake for dread words (Phase 2+, phase-scaled intensity).

**`useSpeedTimer()`** — Speed variant countdown with `onTimeUp` callback.

**`useAchievementQueue()`** — Achievement checking + toast queue processing.

### App Bootstrap & Reliability

- `installGlobalErrorHandler()` (errorReporting.ts) is called at App.tsx module load — thrown global JS errors are captured into the event log via the ErrorUtils handler. **Unhandled promise rejections are NOT captured locally**: React Native never dispatches a browser-style `global.onunhandledrejection` (the old assignment was dead code and is gone), and on Hermes the runtime's rejection tracker is installed by Sentry's ReactNativeErrorHandlers integration alone, so rejections reach Sentry only, never the local `app_error` stream or the Supabase events table. `ErrorBoundary.componentDidCatch` also forwards React render errors through `reportError()` (source `react_error_boundary`), so both async and render-time failures land in the same pipeline. **Render coverage:** `home` and `puzzle` carry their own inner boundaries; an outer catch-all boundary wraps `renderScreen()` so a render error on the secondary screens (settings/stats/ledger/gallery/pit) returns the player home instead of crashing the whole app. The local event buffer is supplemented by configured Sentry native/JavaScript crash reporting; `reportError()` forwards its source and metadata through the Sentry error forwarder. Tracing is disabled.
- Frame-rate monitoring (`performanceMonitor.startFrameMonitoring`) is diagnostic-only — its samples are never read in production — so it is gated behind `__DEV__` (and stopped on unmount) and never runs a perpetual `requestAnimationFrame` loop on a player's device.
- The default export `App` uses `useAppBoot` / `appBootstrap` / `bootCoordinator` to serialize cancellable attempts: recover the local storage journal, install the cloud provider, await any fresh-install restore, run migrations, recover a pending victory, warm settings/cosmetics/hints/entitlements/fonts, then settle pending paid grants before opening MainApp. A retry waits for the prior attempt's durable work; cancellation prevents later stages or a stale ready state. Local recovery failure holds the branded boot screen with Try again rather than opening an unsafe save. Cloud request failures degrade through the provider's bounded requests; there is no longer a 2.5-second restore race that lets a late restore replace an active game. IAP/ads initialization is fire-and-forget after the local boot gates. Notification scheduling waits for hydrated progression. `bootCoordinator` tags the failing stage on every rejection (`getBootFailureStage`) and accepts `{ skipCloudRestore }`; `useAppBoot` reports every boot failure through `reportError` (source `app_boot`, metadata attempt/stage) and offers "Continue without the cloud backup" ONLY for a non-storage failure inside the cloud-restore stage (a `StorageRecoveryRequiredError` there is a local journal/write failure that skipping the stage would replay through migrations anyway, so it stays fail-closed with the local copy); the failed card also carries Try again, a support mailto (`getSupportMailto`, copy from `getBootFailureCopy`) and, for a local failure, **Send your save to support** (`services/supportExport.ts` reads every `wordshift_*` key straight from native storage, leaves out the two cloud-owner recovery credentials, drops the event log and whisper gallery first when too large, and hands the text to the system share sheet). A pending victory that no longer parses or validates is moved to `wordshift_pending_victory_quarantine` (device-local, cleared by Reset All) instead of throwing on every boot; migrations treat a stored `"null"` record as absent. `MainApp` mounts inside a ROOT `ErrorBoundary` (Sentry.wrap is not one) whose reset clears only the board autosave and the home scene snapshot; `rootErrorBoundaryCoverage.test.ts` pins every root overlay inside it.
- Every scheduled notification carries `data.target` (`'daily' | 'home'`); App's `addNotificationResponseReceivedListener` routes taps accordingly, and a **cold-start tap** (notification launched the app — never delivered to the runtime listener) is routed once via `getLastNotificationResponseAsync`, deferred ~1.2s so persistence state hydrates first. Deep links use the same pattern: the Linking subscription mounts once (handler in a ref) and the launch URL is processed exactly once with the same deferral. An AppState listener re-runs the daily launch effects (login reward, streak-freeze check, notification reschedule, stats refresh) when the app foregrounds on a **new local day**.
- Android hardware back normally returns sub-screens home, with puzzle transient state reset; home lets the OS exit. Onboarding, in-flight storage work, mandatory harvest/phase handoffs and ceremony playback have explicit fences. During a ceremony, Back opens its Skip confirmation (or cancels an already open confirmation) instead of dismissing the scene.
- `telemetry.ts`: anonymous-install-id event uploader, fired from the event logger's flush. **Active**: a custom `telemetryEndpoint` in `extra` takes **priority** (one batched POST); otherwise it uploads to the Supabase `events` table (`supabaseUrl`/`supabaseAnonKey` set in `app.json` → `extra`). Only anonymous events (install id, platform, app version, event type) are sent.
- FTUE funnel events: `app_open`, `onboarding_step` / `onboarding_complete` (logged from `setOnboardingStep`), `puzzle_started/completed`, `daily_completed`, `notification_permission_result`, `pit_offer`, `first_manual_harvest` (the pit-economy graduation beat), and `phase_reached` (fired from amberCurrency on each phase advance with `puzzlesSolved` + `installAgeDays` — install date persisted once under `wordshift_install_date` in eventLogger, device meta) — recorded to the local event log.
- **Creator kit** (`creatorKit.ts`): the reveal is gated ~90+ puzzles deep, so press/streamers can never showcase the hook from a fresh install. A `wordshift://creator?code=CODE&era=dusk|shadows|reveal|peace` deep link applies a **coherent late-game snapshot** for the chosen era, then reloads via `Updates.reloadAsync` (falling back to `rebuildSessionFromStorage`). Fully **inert unless `expo.extra.creatorCode` is a non-empty string** (empty in shipping builds = zero risk); the code is validated and a destructive in-game confirm guards the overwrite; the code is never uploaded (the deep-link telemetry redacts the URL). Reviewer instructions live in `docs/PRESS_KIT.md`. App's Reset-All rebuild is the same refactored `rebuildSessionFromStorage({restartOnboarding})` path.
- Purchase funnel events (StoreModal + PatronModal): `store_opened` → `purchase_initiated` → `iap_purchase` (success) ↘ `purchase_cancelled` / `purchase_failed`. Each carries `data.productId` + `data.kind` (`amber`/`hints`/`cosmetic`/`patron`/`adfree`), and failures carry `data.reason`. `telemetry.ts` uploads the full `data` payload into the Supabase `events` table (one row per event, with `install_id`/`platform`/`app_version`), so conversion (opened→initiated→purchased) and drop-off are queryable per product. No PII — anonymous install id only.

### Screen Navigation

State-based routing in `App.tsx`. Screen transitions use an opaque overlay pattern: overlay fades IN (120ms), screen swaps while hidden, overlay fades OUT after a **double `requestAnimationFrame`** (a single frame callback can fire before React commits the batched swap, so the cover began lifting over the outgoing screen). Instant when `reducedMotion` is enabled (and that path also clears any in-flight cover, so toggling mid-transition cannot strand one); low-tier devices get the cover with no reveal signature.

**The cover is painted in the DESTINATION colour while still fully transparent, one frame BEFORE the fade starts** — it used to fade in matching the outgoing screen and then swap colour at full opacity, which is a full-screen colour cut under the cover (bright home `#439cf2` to near-black stats). One frame of lead is required: without it the cover is already ~25% opaque when the commit lands. `getScreenBackgroundColor()` is still the source of the colour.

**`services/screenReady.ts`** is a small arm/mark/wait handshake. The reveal races a destination's own ready signal against a 220ms cap for the four screens that genuinely paint empty first (pit, ledger, gallery, shop — the pit `return null`s until its harvest state lands, the rest start behind a `loading` flag); each marks ready from a `finally`, so a failed read still releases the cover. `waitForScreenReady` returns `null`, not a resolved promise, for anything else, so **home reveals in the same tick with not even a microtask added** — its `homeSceneSnapshot` paints ahead and its cold-read fallback fill is byte-identical to its screen background, so it has nothing to hide.

The cover itself is `components/ui/ScreenTransitionOverlay.tsx`, a `React.memo` leaf: React rasterizes an `Animated` style on EVERY render while a native-driven animation only syncs its JS value back at the end, so any mid-transition re-render committed a stale value (the one-frame flashes). The screen wrapper cannot be memoized (its child is `renderScreen()`), so it keeps its JS value fresh with a single no-op subscriber attached only while its settle runs. A monotonic transition token plus an `{finished}` check guards the pre-cover frame, the cover completion, the readiness race and the reveal, so an interrupted navigation cannot schedule a fighting one. The same-screen early-out applies ONLY to calls with no callback: a callback-bearing same-screen call (a deep link re-serving a board while already on `puzzle`) keeps its cover, or the board would swap in front of the player. The navigation callback is invoked inside a try/catch — it runs before the lines that lift the cover, so a synchronous throw would otherwise leave a full-screen input-blocking cover up forever.

### Victory Flow

1. `isProcessingVictory` lock prevents double-tap; the mid-puzzle autosave is cleared at completion AND at every victory-exit (`startVictoryExitFlow`) so Play can never resume a finished puzzle
2. Record stars, award amber (per-puzzle amber deferred to harvest; one-time windfalls credit the balance instantly — see Offering Pit Economy), check achievements
3. Choreographed sequence: stars pop in with 200ms stagger → modal scales in; the entrance choreography is **tap-to-skip** (tap anywhere → `skipToEnd`)
4. VictoryModal shows: ritual echo chain, named incantation (Phase 2+), words offered count, amber breakdown (itemized — the REAL itemization threaded from `awardPuzzleAmber` as `amberBreakdown` on VictoryData via useGamePersistence, not a local recompute), action buttons
5. Phase transitions are **deferred** — `pendingPhaseTransition` set, VictoryModal shows pit hint, player must visit pit for ward ignition. Confirmation saves the new phase and its owed cinematic together; finishing or deliberately skipping the cinematic acknowledges that queue entry.
6. Post-victory effects: AnimalWhisper (1.2s delay, frequency-gated — see `useVictoryOrchestration`), interjection/home nudge (2.5s delay, 30% chance for the interjection, the home nudge at most once per session; the interjection overlay is pointer-transparent), ritual micro-event (Phase 2+, 60% trigger)

**Victory toast queue (v1.3.2):** the victory chain's transient messages (fresh-variant/streak/quest receipts, speed-record beats, hint-grant receipts, soft nudges...) no longer race each other through direct `setMessage` calls — they enqueue into a **sequential priority toast queue** in App.tsx (rank order receipt > info > nudge; each toast holds the slot `VICTORY_TOAST_DURATION_MS` (1900ms), first toast after a `VICTORY_TOAST_INITIAL_DELAY_MS` (600ms) settle). Priority applies to queued-but-unshown toasts only. The queue is cleared on every victory-exit path, on new-board starts, and on unmount, so a toast can never leak onto the next board.

**Swift Victories** (`settings.swiftVictories`, SettingsScreen toggle, default off): a **routine** win renders a compact instant result strip instead of the full choreography. `isRoutineVictory` in `useVictoryFlow.ts` gates it — the daily, the mandatory-harvest gate, phase transitions, first-completion/milestone/streak-milestone bonuses, quest turn-ins, high-ritual-energy wins (≥ `RITUAL_MICRO_EVENT_MIN_ENERGY`), and the first `SWIFT_VICTORY_MIN_PUZZLES` (20) puzzles ALWAYS get the full modal. The VictoryModal footer carries a one-line Swift Victories affordance from that gate (announced as a switch with its checked state; `getSwiftVictoriesToggleLabel`/`getSwiftVictoriesToggledMessage`), so the faster result strip is discoverable without a trip to Settings. The puzzle `Toast` is phase-aware (`phase` prop → `getToastTheme`, contrast-audited per phase group).

**Victory ownership and optional double:** `useVictoryDouble` retains an in-flight bonus while Next/Home/Collect await it. `claimVictoryDouble(completionId)` reads the amount from the durable victory receipt and commits amber, ledger and `rewardedDoubleClaimed` together. Retrying an interrupted write cannot credit twice, and an old win's callback cannot claim the next win's reward. Generation guards also prevent a dismissed victory chain from reopening its compact/full modal over the next activity. These guards complement the existing `isProcessingVictory` lock.

### Offering Pit Economy (Deferred Amber)

Puzzle completion queues the PER-PUZZLE amber in harvest batches instead of crediting directly. Player must offer batches in the Offering Pit to convert to spendable amber.

**Windfall split (pre-launch fix)**: only the per-puzzle amber defers — `useGamePersistence.recordVictory` enqueues exactly `amberResult.amount` (base + star/streak/challenge/patron/surprise/resonance, plus the variant/fresh-variant bonuses folded into `amount` before enqueue). The one-time WINDFALLS — puzzle-count milestone, first-completion, and streak-milestone bonuses — credit the spendable balance IMMEDIATELY inside `awardPuzzleAmber`, regardless of `creditToBalance` (a "+150 Century milestone!" is a moment, not a harvest, and must be spendable without a pit detour). `VictoryData.amberEarned` / `AmberBreakdown.total` remain the FULL earned receipt (queued share + instant windfalls), so the VictoryModal itemization still sums exactly; `totalAmberEarned` counts every part exactly once either way; windfalls stay amber-only (never phase progress). The auto-collect window credits batch + windfalls to the same total as before (no double credit, no loss); routine wins on the compact swift strip can never carry a windfall (`isRoutineVictory` excludes milestone/first-completion/streak-milestone wins), so its "gathered for the pit" label stays honest. Pinned by regressions in `amberCurrency.test.ts` + `useGamePersistence.test.ts`.

**Flow**: Puzzle complete → `enqueueHarvestBatch()` (per-puzzle amber only) → VictoryModal shows "Collect Now" → pit screen → tap floating words to devour → `offerBatch()` credits amber.

**Crash-safe crediting**: `offerBatch`/`offerAllBatches` don't just delete the batch — the released amber moves into a `pendingCredits` ledger **inside the same persisted write**, and the pit credits via `awardBonusAmber` then acks (`acknowledgeBatchCredit`); a kill between offer and credit is recovered by `reconcilePendingCredits()` on pit load (orphaned credits re-apply, the ledger entry is the dedupe). The player's **first real manual offer** logs a `first_manual_harvest` funnel event (and sets the mandatory-harvest learned flag, below).

**Auto-collect window**: through the first `AUTO_COLLECT_PUZZLE_LIMIT` (8, `gameBalance.ts`) puzzles, amber auto-credits without a pit visit (the auto-collect path sets `VictoryData.autoCollected`). The VictoryModal shows an in-world reason via `getAutoCollectCaption(phase)` ("The house carries your words down to the pit for you, for now.") — lore, never a "tutorial" voice — so the automatic reward reads as the house doing the ritual labor for a newcomer.

**Mandatory first-harvest gate (repeat-until-learned)**: every victory past the window with a real batch waiting (`completedTotal >= AUTO_COLLECT_PUZZLE_LIMIT + 1`, outside onboarding, no phase-transition ceremony already claiming the pit, `!hasSeenMandatoryHarvest()`) sets `VictoryData.mandatoryHarvest` in the App victory chain. The VictoryModal then **forces** the pit before the player can continue: it hides Next Level / Home / Share (same `mustVisitPit` gate the phase-transition ceremony uses) and shows `getMandatoryHarvestText(phase)` + `getMandatoryHarvestCTA(phase)` as the only action — teach the pit by using it, with a lore beat instead of a passive Fox card. **The `wordshift_mandatory_harvest_seen` flag means LEARNED, not shown**: it is set only when the player completes a real manual offer at the pit (`markMandatoryHarvestSeen` in OfferingPitScreen's `tryFinalizeBatch`/`handleHarvestAll`, skipped during onboarding) — never at gate-decision time — so the gate re-fires on every eligible victory (standard, daily, variant) until a genuine harvest happens, and no interruption can silently consume the teaching beat. Escape hatches are closed in App.tsx: hardware back over a pit-mandatory victory routes to the pit (same as the CTA), deep links and notification taps are swallowed while the gate modal is up, and `maybeShowVictoryInterstitial` exempts `mandatoryHarvest` exits. A **Fox pit-arrival intro** completes the beat in-world: while the harvest is unlearned, arriving at the pit with batches waiting (outside onboarding, no phase ceremony claiming the pit) pops a FoxGuide dialogue teaching the tap-to-offer (`shouldShowHarvestPitIntro` pure decision in OfferingPitScreen + `getMandatoryHarvestPitIntroLines` in phaseNarrative) — the victory gate says the house stopped carrying, Fox at the pit says what to do about it. Repeat-until-learned like the gate: dismissing the card does NOT set the learned flag, only a real offer does, and the words stay tappable behind the card. A **one-time home safety net** (`harvest_gate_intro` in HomeScreen, own flag `wordshift_harvest_home_intro_seen`, copy `getHarvestHomeIntroLines`) has Fox explain the pit from home if the player still lands there unlearned with batches waiting; dismissing it does NOT set the learned flag. A **gentle heavy-pit nudge** (`harvest_heavy_nudge`, once per app session, no persistence) fires when `pendingAmber >= HARVEST_NUDGE_MIN_AMBER` (150, gameBalance) after the pit is learned (copy `getHarvestNudgeLine`). The learned flag stays deliberately **decoupled** from the legacy `wordshift_pit_harvest_intro_seen` (the old passive puzzle-8 Fox card set that legacy flag on existing saves; reusing it would have suppressed the gate for returning players — pinned by `mandatoryHarvestGate.test.ts`). All three keys are cloud-synced + cleared by Reset All.

**Pit Features**: Flying mini candy-tile words, tap-to-devour spiral animation, multi-layered pit glow (4 concentric ovals), ward marks (7 circles showing phase progress), ward ignition ceremony for phase transitions, phase-aware background images.

### Phase Transition System

**The reveal waits for the whole house.** Phase 4 is the one transition that additionally requires all thirteen residents to be recruited (`FULL_HOUSE_PHASE` in gameBalance, `isRevealHeldForHouse`/`countResidentsHome`/`countResidentsAway` in `amberCurrency.ts`), so the last recruit is present FOR the reveal instead of walking in after it. The hold withholds the OFFER at the single producer (`awardPuzzleAmber`, the only writer of `pendingPhaseTransition`) and **also reports the previous phase back to the caller**: `useGamePersistence` takes `result.newPhase` on the not-pending branch, so a held result still naming 4 would drive the live session into the reveal it is being denied (dark theme, robed sprites, phase-4 copy and dialogue budget) with durable phase still 3 and no ceremony, and would silence interstitials for good via App's `phase >= 4` ad policy. Gating at CONFIRM time instead is an unrecoverable soft lock: `mustVisitPit` hides Next Level / Home / Share on the victory screen and the pit's `navigationBlocked` refuses every exit including hardware back while a transition is pending. Nothing already granted is revoked: `confirmPhaseTransition` does not consult the hold, so a save carrying a pending 4 from an earlier build still commits, and a save already at phase 4 or 5 is untouched. `creatorKit` passes `ignoreFullHouseHold` because its win loop runs before it buys any room; it is the only caller that may. **No deadlock:** `isDescentTrioHeld` gates the last three rooms on WEIGHTED progress (never `currentPhase`), and the paid Reserve/Skip/Speed-up paths refuse the trio below `currentPhase` 3 while the hold can only engage AT 3, so every route to the last residents is open exactly while the hold is on; the remaining cost is amber, and per-puzzle pay, quests and dailies are unbounded (`MILESTONE_BONUSES` is NOT - it ends at 930 solves). **The accepted cost:** the reveal now follows the purse. Residents are bought and much of amber income accrues per real-world day, so measured on `economyJourneySimulation`, free 8/day moves 96 -> 112, Patron and Supporter 96 -> 104, a player who skips quests and dailies 96 -> 152, one continuous 240-win session 96 -> 216, and the casual 2/day target 90 -> 94. Paying therefore reaches the reveal ~8 wins sooner than the same free schedule, and because the endgame chain sits behind phase 4 the ending moves with it. That is a deliberate owner decision, not a regression; the simulation carries the numbers and `homeWorldData.test.ts` pins that the last room gate (92) stays above the reveal floor (90), which is what makes the house, not the floor, the binding constraint. The house is consequently ALWAYS complete before Phase 4 commits, so `canQueueHouseCeremony`'s hold now fires on every playthrough.

**Ember's full-house beat** (`getFullHouseIntroLines`, `introContext: 'full_house_intro'`, one-time key `wordshift_full_house_intro_seen`, cloud-synced + Reset All) is the unread-conversation warning, and it fires on the HOME screen the first landing after the last resident moves in while the world is still Phase 3 and no transition is pending. Home is the only place it can honestly live: after the reveal is offered there is no moment at which the player can go and listen, so a warning raised at the pit would be a choice with one real option. It counts residents whose home badge is LIT (`animals.filter(a => a.hasNewDialogue)`), so the number always matches what the player sees when they look up at the house, dialogue cooldown included; a separate unread-line count would disagree with the badges after a full round of visits and send the player to doors that open on nothing. Its copy promises the HOUSE, never a number of wins: the beat fires when the last resident arrives (92 solves) while the reveal also needs the weighted threshold, and waiting for both is impossible because the moment both hold the reveal is offered on that same win, leaving no landing to speak on. It shares the `landingIntroSpentRef` budget, carries the gated-room intro's `GATED_ROOM_INTRO_SETTLE_MS` re-check (the resident who completes the house is bought on this screen, and `useUnlockFlow` publishes the new roster BEFORE arming that resident's own introduction on a 300ms timer, so without the settle Ember would displace the newcomer on their own doorstep), depends on a derived `houseIsWhole` rather than the `progress` object (which HomeScreen replaces on every committed dialogue line, quest claim and menu amber change), and marks its flag on ACKNOWLEDGMENT, never at presentation. The pit meanwhile explains a full-but-inert circle with `getPitHouseIncompleteHint` ("The circle is full. The house is not."), and its wards read the live `phaseProgressFraction` prop, never a durable snapshot (a snapshot goes stale the other way: a pending transition clamps the stored fraction to 1 and `confirmPhaseTransition` resets it to 0, so a mount-time copy would keep a just-ignited circle full and let it claim the house was holding it). The held path's own staleness is fixed at the source: `awardPuzzleAmber` now RETURNS `phaseProgressFraction` and `useGamePersistence` mirrors it on every award, where it previously only set it alongside a pending transition; a held win reports `phaseTransitionPending` false, so without that the pit drew an under-lit circle and withheld its explanation until a relaunch. The `dusk` and `shadows` creator-kit eras keep their modest purses: measured through the real pipeline the hold makes them a longer road to the hook (~20 self-funding wins from shadows against ~5 before, ~59 from dusk against ~40) but never a closed one, and the `reveal` era exists for showing the reveal itself.

Phase transitions are deferred. When `phaseProgress` crosses a threshold, `pendingPhaseTransition` is set. At the pit the player confirms ward ignition; `confirmPhaseTransition()` atomically saves the new phase and a `phase` entry in `HomeWorldProgress.pendingCeremonies`. `ceremonyPlayback.ts` presents the saved queue in order and acknowledges the exact event only after completion or confirmed Skip. House completion, Arrival, post-arrival and New Cycle share this queue. Navigation and mounting a scene do not consume it; failed acknowledgement keeps the handoff open for retry. A cold restart replays an unfinished event from its beginning, rather than restoring an exact page. Legacy saves are not backfilled with every historical phase event.

Phase completion or confirmed Skip atomically replaces the phase entry with a `phase_reaction`, ahead of any queued house ceremony. A recruited resident immediately acknowledges the change in `PhaseReactionDialogue`; Continue acknowledges that response before other scenes or share prompts proceed. Phase 5 receives its response after `post_arrival`, respecting the saved boundary. `phaseTransitionReactions.ts` owns this separate copy; ordinary conversation read IDs, introductions and choices remain untouched. Restart reopens an owed response, and previously completed phases receive no backfill.

**Reading and interruption controls (`PhaseTransitionOverlay`):** every phase, house, Arrival, post-arrival and New Cycle passage waits for Continue. Back returns to the previous passage; Android Back does the same after the first page and asks for skip confirmation on the first. Skip always asks for confirmation. Navigation has a 350 ms duplicate-tap guard, and handlers reject stale event identities. Authored timings control visual effects only, never reading time. Backgrounding pauses effects and preserves the mounted page/scroll position; a temporary save overlay suspends it too. Reduced motion affects effects, not navigation. Revisiting a passage does not repeat its one-shot sound cues. Scene art and backdrops accompany the responsive reading layout; do not return to an empty full-height text card or make text unreachable at large font sizes.

Ward marks: 7 circles hugging the pit opening's own ellipse (same radii + a small uniform offset, `PIT_WARD_RIM_OFFSET` — never a differently-proportioned arc), set into a **ward ring** drawn on that same radius (circle + `scaleX`, no SVG; a soft halo ring behind it is the Android-safe glow technique, never `shadowRadius`) whose brightness scales with `phaseProgressFraction`. The ring and the marks share one `wardsVisible` gate (`phase < 4`): the marks used to additionally require some progress, so a player at exactly zero progress saw no track at all, and each mark now sits on a dark seat so an unlit station reads as a station rather than a gap. Phase-aware colors (turquoise → purple → crimson). Pulsing when transition ready. **Continuous progress in every phase**: the next unlit ward "charges" with partial-opacity lit color proportional to sub-dot progress (`wardChargeFraction`), and the cryptic hint line appears from 15% progress — the later phases are 3-5x longer than the first, and whole-dot steps alone read as stalled.

**Reserve-ahead (pay now, build at the gate):** the gates are tuned for a baseline earner, so a fast/skilled player (HARD + achievements + quests) reaches a gated room's amber cost well before its level gate and would otherwise sit on idle amber behind a wall. Reservation rides in `wordshift_home_progress` (cloud-synced; cleared by Reset All's `clearProgress`). Covered by `homeWorldData.test.ts`.

**Skip the wait (pay a premium, unlock NOW):** alongside Reserve, a gated room the player can afford at a **premium** offers a **Skip the wait** shortcut — unlock it immediately, bypassing the level gate. `getUnlockSkipCost` = `ceil(cost × (1 + UNLOCK_SKIP_PREMIUM))` (premium = **1.5** in `gameBalance.ts` since the September 2026 launch-readiness pass — skip = 2.5× build cost, so the gated builds at 200-550 amber skip for 500-1,375; it was 0.5 / 1.5× from v1.3.2, which the economy simulation showed a casual 2/day player could afford at every non-trio gate from solve ~13); `canSkipUnlockGate` mirrors `canReserveUnlock` but requires the premium be affordable and no reservation pending (skip and reserve are mutually exclusive); `skipUnlockGate` spends the premium via `unlockRoom`/`unlockAnimal` and unlocks right away (celebration + character intro like a normal purchase). The premium is **convenience pricing**: a meaningful step over (cheaper) Reserve so the gate keeps its shape, priced as a real decision against the Phase-2 House Upgrades rather than loose change — tune post-launch on `unlock_purchased.skippedGate`. From Phase 2 the locked-room card also carries a House Upgrades pointer row (`getHouseUpgradesPointerLabel`) beside the Unlock Progress modal's, so a player holding idle amber at a gate is shown the recurring sink. Surfaced in the room-unlock modal as a secondary outlined-amber button *below* the (cheaper) Reserve button — `useUnlockFlow` exposes `canSkip`/`skipCost`/`handleSkip`; copy via `getSkipGateText`. **Speed up a reserved room:** once a room is *reserved* (Skip is then hidden, since reserve already paid the base cost), a "Speed it up" button lets the player pay only the remaining premium (`getReservedSkipCost` = skip cost − build cost) to unlock it now — `canSpeedUpReservedUnlock`/`skipReservedUnlock` (spends the delta, `claimReservedUnlock`s it, clears the reservation); total paid equals a direct skip. `useUnlockFlow` exposes `canSpeedUpReserved`/`reservedSpeedUpState`/`reservedSkipCost`/`handleSpeedUpReserved`. **The refusal states each other**: `getReservedSpeedUpState` returns `'ready' | 'not_yet' | 'need_amber' | 'none'` and `canSpeedUpReservedUnlock` delegates to it, because the descent-trio phase guard (amber must never summon the last three rooms during the bright days) sat one line ABOVE the affordability compare — so a player at Phase 0 holding 13,252 amber against a 225 premium had their balance never read, saw no button, and was told by unconditional copy to come back "once you can afford it". The guard stays; the copy now branches (`getReservedSpeedUpNotYetText` carries NO price, since no amount of amber buys past it), the Unlock Progress modal's non-interactive "Speed up N" price tag only renders on `'need_amber'` (it is a `<View>` with no `onPress`, so on `'not_yet'` it advertised a purchase that does not exist), and the locked-room lead line runs through `getLockedRoomReasonText` instead of unconditionally claiming the player needs more amber. The **Next Unlock meter** measures the BINDING constraint too: it was amber-against-cost unconditionally, so a reserved room whose cost was already spent pinned the bar full at "13252 / 450" while the player waited on 84 solves; it now counts solves when a level gate or live reservation is the blocker (`getNextUnlockMeterText`), and its trough took the quest bar's `amberTint`/`amberTintBorder`/`amberText` pair plus a real outline (the old `pillBg`-on-`sectionBorder` fill sat at 1.14-1.27:1 through phase 3, so full and empty were the same picture). Amber-only (never cash) and never feeds phase progress. Covered by `homeWorldData.test.ts`.

**First-gate lore intro (one-time, Fox-led):** the first time a level-gated room actually *blocks* the player (the next unlock is a `type:'room'` with a `minPuzzles` gate and `puzzlesSolved < minPuzzles` — the Jungle Hammock at level 19 by default), a one-time HomeScreen intro fires (same `introOverrideLines` mechanism as the challenge/daily/journal intros): Fox explains the wait in-world (the house needs *time and words offered*, not just amber) and points at Reserve (set the amber aside now, it rises on its own) and Skip (press it to completion now, though the house asks a good deal more; the copy no longer minimises the premium now that Skip costs 2.5x the build). Gated by `hasSeenGatedUnlockIntro()`/`markGatedUnlockIntroSeen()` (`introContext: 'gated_room_intro'`); it fires the moment the gate blocks (below `minPuzzles`) **regardless of whether the player can yet afford Reserve/Skip** — a fast solver reaches a gate with empty pockets and previously got NO explanation at all (the old `progress.amber >= cost` gate only spoke long after the frustrating first-wall moment; a bare locked room read as a dead-end). The intro copy is deliberately **conditional** ("if you have the amber, you need not wait...") so it lands as expectation-setting, not a button-press instruction, even when nothing is affordable yet. The only reason the old code waited was a flicker with the just-unlocked animal's own intro (the previous animal unlocks seconds before the gated room becomes next, and its intro opens on a 300ms delay in `useUnlockFlow`); that is now dodged with a **`GATED_ROOM_INTRO_SETTLE_MS` (500ms) settle delay that re-checks the shared intro surface via `introSurfaceBusyRef`** so the animal intro always wins that window (and if it claims the surface, the gated intro simply re-fires once the surface frees, since `markGatedUnlockIntroSeen` runs only when the player actually closes the card). It fires whether the player is idling on home **or** has already opened the room's unlock modal (the intro dialogue at line ~2230 renders on top of the room-unlock modal at line ~1977, so dismissing it reveals the Reserve/Skip buttons underneath) — the blocking window can be brief (unlock the prior animal, immediately tap the gated room, reserve/skip), so it must not be suppressed while that modal is open. Key `wordshift_gated_unlock_intro_seen` is cloud-synced + cleared by Reset All. Covered by `gatedRoomIntro.test.ts`.

### Dialogue System

**1,742 base dialogues** (134 per animal across 13 animals; every line scored against a McKee-based dialogue rubric) + **260 post-revelation** (20 per animal) + **130 Phase-2 exhaustion-pool lines** (`PHASE2_EXTRA_DIALOGUES`, 10 per animal):
- Phase 0: 24, Phase 1: 28, Phase 2: 22 (incl. question-web hook), Phases 3-4: 30 each, Phase 5: 20 each. Each phase block is written as session-sized mini-chapters (3 lines/visit at Phases 0-1, 5 at Phases 2-3, 6 at Phase 4) with end-of-session hooks and continuing story threads. **Doubling shifted every phase-start index — dataMigration v4 (`remapDialogueIndexV4`) remaps saved `lastDialogueRead` values to the same (phase, offset) position; never resize a phase block without a companion migration.**
- Counts are enforced by `configValidation.ts` (`EXPECTED_DIALOGUE_COUNTS_BY_PHASE`, `EXPECTED_PHASE2_EXTRA_PER_ANIMAL`=10) — update it when adding lines

**Sequential reading and persistence:** `conversationProgress.ts` selects the earliest eligible unread line from each resident's 134 regular lines, up to their effective phase (capped at 4 for this corpus). `conversationReadIds` and `conversationReadVersion: 1` live inside the existing synced `wordshift_home_progress` record. Only Next after the final page creates a receipt, including for the last available line; journaled writes are idempotent and reject stale-cycle or out-of-order completions. Close, backdrop dismissal, switching friends and interrupted typewriter reveal leave the current line unread. A reopened unfinished line starts at its first page. Legacy `lastDialogueRead` values remain compatibility/pool counters; they cannot prove earlier lines were read because older builds forced jumps. An absent read ledger starts empty once, which can repeat genuinely read material but recovers potentially skipped lines without resetting the house, amber, introductions or choices. New Cycle clears the read-ID ledger and changes the cycle guard; Reset All clears the owning progress record.

**Session mechanics and badges:** normal phase-aware limits remain 3–6 lines per session, with 2–5 puzzles between sessions and the existing new-resident grace period. **Backlog pacing** (`getConversationBacklogPlan` in types/homeWorld.ts): while a resident's next unread regular line belongs to a phase two or more behind the house (a late recruit met at Phase 3 reading their introduction, or a friend long left unvisited), or, once the house is at Phase 4, to ANY earlier phase (so lagging residents hear their reveal chapters before the Arrival rather than after it), the visit gains `BACKLOG_BONUS_DIALOGUES` (5) lines and the rest between visits is capped at `BACKLOG_MAX_PUZZLES_BETWEEN_SESSIONS` (2). Whoever resolves the next line reports it to the session layer (`updateConversationBacklog`: useDialogueFlow's `getRegularConversation`, called before every availability check, and `getAnimalsWithStatus` before the badge cooldown test); the plan relaxes by itself as the reader catches up, and nothing is skipped. The finale never waits on reading: it arms on the dwell wins and the solve floor alone. A pending ordinary welcome is available through cooldown. After the welcome, a badge means eligible unread regular material, an unanswered available choice or new pool content, subject to the same session availability used on tap. Locked-resident references are deferred without receipts and become readable when their required resident joins. When finite regular content is exhausted, the animal says the current-phase caught-up line instead of repeating its last passage. Phase-2 exhaustion and Phase-5 Tending follow the eligible regular corpus. "Visit next friend" closes without consuming the current line and opens the next unlocked resident with news through the normal availability check. The former terminal-read-on-Close rule is retired.

**Rich interaction layers**:
- **Conversation shortcut:** the footer says `Talk to <name>` and uses HomeScreen's complete visit path after releasing the previous dialogue. Pending gifts are presented before ordinary dialogue, and unseen residents receive their full introduction. Rapid shortcut taps share one handoff; opening failures provide retry guidance. The shortcut never consumes the line being left.
- **Cross-animal references**: Phase-scaled frequency (20% → 60%). Vanguard animals get a guaranteed first reference at each new phase. Dynamic references filter by `unlockedAnimals` (multi-name lines must set `mentions` to the latest-unlocking animal named). Static base lines use `requiresAnimals`: `getNextAnimalConversation` can select later eligible material, but never records blocked lines as read; the deferred line returns once its referenced residents are present. `resolveDialogueIndex` remains a compatibility/presentation helper, not authority to consume dialogue. Coordinated event lines are name-scanned at delivery time. The gating checks prevent references to residents the player has not met.

## Incantation System (Puzzle-Narrative Connection)

The core system making puzzles feel like rituals:

- **Ritual Word Memory**: Every word formed is recorded (capped at 500). `recordRitualWords()` in `amberCurrency.ts`.
- **Ritual Echo**: VictoryModal shows completed word chain. Styling evolves: bright candy → muted → dark/vertical arrows. Header: "Your Word Journey:" → "The Offering:".
- **Named Incantations** (Phase 2+): Deterministic chain names. Phase 2: "The HEAT Dance". Phase 4: "Offering: VOID to DOOM".
- **Ritual Energy**: Dread word presence scored 0-10. Each point adds 0.1 to `phaseProgress`. High-energy puzzles (7+) trigger micro-events.
- **Word Ledger**: Scrollable screen of all formed words. Dread words highlighted at Phase 2+.
- **Animal Whispers**: 364 lines (5 per animal per phase, except Phase 4 which has 3 each; 13 animals × 6 phases). Prefers animals matching puzzle trigger words. Frequency-gated per win since v1.3.2 (~45% phases 0-3, ~60% phase 4, always phase 5 — see `useVictoryOrchestration`).
- **Dread Word Visual Feedback** (Phase 2+): Crimson pulse overlay on dread word formation. Phase-scaled opacity (0.10 → 0.25).
- **Arrangement Pattern** (Phase 2+): Visual sigil lines connecting rooms on house exterior.
- **Room Word Echoes** (Phase 2+): Faint puzzle words scattered across room backgrounds.
- **Phase-Appropriate Windows** (Phase 1+): the room interiors are painted with bright day-sky windows that read as noon under a dusk/night sky. `processRawWorldArt.mjs` extracts a per-room window-sky mask (`assets/rooms/windows/<room>.png`, white on transparent — largest blue blob + mullion-split panes merged, clouds within the region included, monitors/globes/plants excluded) for the rooms with a clear sky window (`cozy_den/kitchen/study/office/garden`); the aquarium's water, the desert's already-night sky, and windowless rooms are deliberately untreated (verified against a per-room detection montage). RoomView overlays the mask with a `tintColor`+opacity from `WINDOW_TINT` so just the window sky recolors to the phase (day-blue → dusk rose → night dark) while the mullions/curtains and the warm lit interior (fireplace, lamp) stay. Since the house is a cutaway, windows show the view OUT — they darken at night, they don't glow.

### Move Resonance (evaluative depth)

The puzzle-side complement to the ritual systems: the game notices when the player **chose the deep word on purpose**. On each committed formed-word move, `usePuzzleGame` runs `collectDistinctOutcomeWords` from the PRE-move step state (the `hasAnyValidMove` enumeration, but collecting the distinct valid outcome words instead of short-circuiting — ~20-40 sync dictionary lookups once per commit; double-shift passes the MID-step state so the enumeration mirrors the completed step's real remaining decision space; Unbroken Weave filters spent letters). `isResonantChoice(chosenWord, outcomes)` (both pure/exported) then marks a **resonant choice** when (a) a real choice existed (2+ distinct valid outcome words), (b) the chosen word carries dread weight (`getWordPhaseTier >= 1`), and (c) no available alternative ran deeper (chosen tier ≥ max tier among outcomes). Consequences:
- **Amber**: `RESONANT_MOVE_AMBER` (2) per resonant choice, capped at `RESONANT_BOARD_CAP_AMBER` (6) per board (`resonanceAmberForCount`) — a garnish, not a farm. Threaded from the completing move (`resonantChoiceCount`/`resonanceAmber` on the move result) through `useGamePersistence.recordVictory` into `awardPuzzleAmber({resonanceBonus})` (defensively clamped to the cap), additive to the REWARD only — like the Patron/surprise bonuses it **NEVER feeds phase progression**, so weighing options pays amber, never a faster descent. Itemized in the VictoryModal breakdown under `getResonanceBonusLabel(phase)` ("Deep words" → "Resonant words" → "Words it wanted").
- **Acknowledgment**: a resonant commit REPLACES the normal move message with `getResonantMoveMessage(phase)` for that commit only (never stacked with the pool draw; combo/streak bookkeeping still runs identically).
- **Records**: the board tally accumulates into a lifetime mastery stat (`recordResonantChoices`/`getResonantChoices` in `masteryRecords.ts`, migration-safe) and, on daily wins, an optional spoiler-safe `resonantChoiceCount` on the day's `dailyLadder` entry (stored only when positive — a count, never the words).
- **Bookkeeping**: per-move resonant flags align with `moveOutcomes`, so an **undo pops the flag and decrements the tally**; like moveOutcomes, resonance is NOT persisted — a restored autosave board restarts at zero. **Excluded entirely**: Blind Offering (the chain is judged once at the end — mid-board evaluation would leak validity) and the finale board (never pays it).

### Cottage Pixel Skin (`scripts/tools/generateUiPanels.mjs` → `assets/ui/panels/` + `theme/pixelSkin.generated.ts`)

- **Generator**: `node scripts/tools/generateUiPanels.mjs` (pure Node, dependency-free PNG writer) draws full frame masters on an art-pixel grid (1 art-px = 3dp, baked at 9 real px/art-px for crisp @3x) and slices the 9-slice pieces from them, so seams match by construction. Edge strips are uniform along their stretch axis (all decor — nail heads, grain dashes, stepped radius-4 corners — lives in the fixed corner tiles): stretch-safe on Fabric. Warm near-black outlines (never #000), top-lit wood band, side-dependent recess transition. Re-run after palette changes; it also regenerates `src/theme/pixelSkin.generated.ts` (typed registry with static requires + dp constants).
- **Five materials, one geometry**: bright (phases 0-1) / dusk (2) / storm (3) / dark (4, ash paper + crimson accent, ink polarity flips to cream) / serene (5, mauve). ## Onboarding (Cold-Open Intro)

**The shipped flow is a COLD OPEN, not a guided tour** (`OnboardingStep` in `services/onboarding.ts` + `useOnboardingFlow.ts`): a fresh install (`not_started`) resolves to `cold_open_puzzle` and lands DIRECTLY on curated EASY board 0 — no home screen first, no named guide. A warm, **unnamed** voice sets the one rule in a single line (`COLD_OPEN_INSTRUCTION` — it never points at the exact letter, the solve stays the player's own), reacts once with delight on the first committed move (`COLD_OPEN_FIRST_MOVE`, keyed on history length reaching 1 so it fires exactly once and never stomps invalid-drop feedback), and — added in the v1.3.2 pass — teaches the marks once on the FIRST letter pick-up before any commit (`COLD_OPEN_PREVIEW_TEACH`: green check / red cross previews + undo, ref-guarded to once, fired while the ghost previews are actually on screen — the tools are taught at the exact moment they first matter). Fox appears only AFTER the first win:
1. `cold_open_puzzle`: the self-directed opener board. The victory Continue routes to `home_empty` (board cleared).
2. `home_empty` → `fox_invited`: the empty home; tapping the den invites Fox, who acknowledges the already-solved puzzle — the player learns WHO was speaking, turning the opener into the quiet hook: something warm was already helping before it was ever invited in. Ember's faint wrong-note ("I have been hoping for someone like you for the longest time") closes the beat.
3. `going_to_pit` → `pit_intro` → `pit_offering`: Fox explains the pit in ONE card, then a standing FoxGuide prompt (`pit_offering_prompt`, no continue button until offered) tells the player to **tap each floating word** to offer it — the step only advances once every word is devoured (no auto-offer; a fallback only arms if the step is reached with nothing offerable). A **stalled-pending safety net** (`PIT_ONBOARDING_STALL_RESCUE_MS` = 30s, reset on every successful devour) auto-offers the remainder and completes the step so a confused player can never soft-lock onboarding. Because every word must be tapped **individually** here (no Offer All, no continue button until they are gone), the tutorial words do NOT take the pit's random scatter: `services/pitOnboardingLayout.ts` seats them on a grid of non-overlapping cells, one per row until the rows run out and a second column starts, with the vertical bob dropped and the horizontal drift bounded to the cell. The band is the screen between Ember's prompt card and the pit, and its top follows the card's **measured** bottom (`FoxGuide`'s `onMeasureBottom` -> App's `pitPromptBottom` -> the pit's `onboardingPromptBottom`), because the card's height depends on how its authored line wraps: the old fixed `SCREEN_HEIGHT * 0.30` cleared it on a 844pt phone by 9pt and buried the band under it on a short one, where a word is unreachable and only the stall rescue ends the step. Both occlusions (card-over-word, word-over-word) are pinned geometrically in `e2e/onboarding.spec.ts` and by `pitOnboardingLayout.test.ts`; the random scatter is unchanged everywhere else.
4. `returning_home` → `unlock_explained` → `complete`: two Fox beats — the happy loop plus where the pit entrance lives (the in-world path is the only route back to the pit), then "come back each day".

During onboarding: simplified UI (no difficulty selector, stats, NEW button). Backward compatible with the legacy tutorial flag (old players who completed the original tutorial skip straight to `complete`). Persisted via `wordshift_onboarding_step`; `onboarding_step`/`onboarding_complete` funnel events fire from `setOnboardingStep`. **Legacy-step compatibility:** the old guided-puzzle steps (`going_to_puzzle`/`puzzle_tutorial`/`puzzle_complete`) remain VALID states with their Fox lines intact, so installs interrupted during the previous onboarding resume safely — the guided-board machinery (`tutorialGuidance` glow highlights, the compact FoxGuide card that dodges the active board zone via `tutorialFoxAnchor`, the ✓/✗ reinforcement beat) still serves that resume path. **Resume resilience:** transient steps only exist for a `setTimeout` window and have no owning screen on relaunch; `useOnboardingFlow.normalizeResumeStep` snaps them forward to a stable target, and `App.tsx`'s resume effect routes `cold_open_puzzle` through `resolveColdOpenLaunchRoute(hasPlayableAutosave, puzzlesSolved)` — a persisted win beats a stale PLAYING autosave (→ `home_empty`), else restore the exact autosaved opener board, else start curated board 0 fresh; the legacy `puzzle_tutorial` step re-inits a live guided board — so a kill mid-onboarding can never strand a new player on a dead screen. **Skip is two-step from every step**: on the cold-open board a Skip chip confirms via a game alert (`handleColdOpenSkipPress`, copy via `getSkipConfirm*` in phaseNarrative — "Keep going" prominent, "Skip it all" quiet); the FoxGuide steps confirm in-card. Only the confirmed skip runs the **clean exit**: it cancels pending step timers, persists `complete` (which atomically collapses every guidance surface), abandons the opener/guided board (`clearBoard` + `clearPuzzleState`), and lands on the full home screen. FoxGuide renders nothing when it has no text (no empty-card state), and its cards are the light lavender style at every anchor (no dark variant). A session that contained onboarding also defers the daily-login claim to the next launch (see Currency).

## Key Services Detail

### Puzzle Generation (`localGenerator.ts`)

Two-track generator with pre-computed indices:

- **Adjacency index**: `getInsertionIndex(wordLength)` — O(1) lookup for letter insertion candidates. Cached per word length.
- **Removal index**: `getRemovalIndex(wordLength)` — inverse mapping for reverse chain generation.
- **Standard**: Forward DFS, 2.5s timeout, 3 candidates, score ≥ 45. Anti-boring detection (penalizes S→plural, ED→past tense, etc.). **Forced-start (echo) boards** relax acceptance to `FORCED_START_MIN_SCORE` (20) — a `forcedStartWord` shrinks the candidate space so the normal 45 floor would starve echo-puzzle generation. **Multi-route final pick (v1.3.2)**: the exported pure helper `pickMultiRouteCandidate<T>` runs at the FINAL best-of-3 pick — the highest-scoring candidate with `completePathCount >= 2` (via `analyzeStandardBranching` with tight caps `{pathCap: 8, stateCap: 500}`) wins, and the best single-route ships when none qualifies. **Trap tie-break (Depth Levers Pass)**: an optional `hasTrap` predicate (`trapStepFraction > 0`) breaks EXACT score ties among qualifying multi-route candidates toward the trap-bearing one — score stays primary, and single-route candidates never gain from traps. Skipped entirely for `forcedStartWord` (echo) boards, `requireReverse` chains, and <2-candidate lists; the analysis runs after the search loop ends, so timeout/search behavior is untouched. The double-shift generator's identical-looking pick block deliberately does NOT get the preference (standard-only by design).
- **Reverse**: `generateReverseChain()` — random sampling + `isReverseSolvable()` validation. 25s timeout. `relaxBoring` flag widens pool.
- **Double shift**: `generateDoubleShiftPuzzle()` — 2-letter moves, `getDoubleInsertionIndex()` for pair lookups. Position-based locking via `receivedPositions`.
- **Phase-tiered dread words**: 615 words in 4 tiers. Scoring: `phase² × 2.5 × proximity_multiplier`.
- **Quality scoring**: Position preference (middle > edge), semantic journey bonus, word freshness, dread tier proximity.

### Amber Currency (`amberCurrency.ts`)

Core economy manager. Key functions:
- `awardPuzzleAmber()` — Returns balance/phase/streak + `phaseTransitionPending`. Deferred: sets `pendingPhaseTransition` instead of bumping phase. Crediting split (pre-launch fix): with `creditToBalance=false` (the recordVictory path) the per-puzzle `amount` stays deferred for the pit, but the one-time windfalls (milestone / first-completion / streak-milestone) credit `progress.amber` immediately either way — amber-only, never phase progress, `totalAmberEarned` counts each part exactly once. Takes `options.resonanceBonus` (clamped to `RESONANT_BOARD_CAP_AMBER`, returned itemized as `resonanceBonus` in the breakdown; additive to the reward only, never phase progression — see Move Resonance).
- `confirmPhaseTransition()` — Commits the pending phase, cleared fraction and owed cinematic together. A recovered confirmation returns the same transition while its queue entry remains pending. `getPendingCeremonies()` / `acknowledgeCeremony(id)` / `queueHouseCeremony()` own delivery; animations never set seen flags directly.
- `applyVariantAmberBonus()` — Variant bonus: the full configured multiplier always applies (the old anti-farm decay is REMOVED) plus a flat once-per-local-day-per-variant `FRESH_VARIANT_BONUS_AMBER` on top (`freshBonus`/`isFresh` returned so the VictoryModal can surface the moment). Amber only; never phase progress.
- `awardBonusAmber()` — General-purpose credit (streak milestones, etc.).
- `recordRitualWords()` — Record words, queue triggers, accumulate ritual energy.
- `consumeTriggerWords(animalType)` — Per-animal trigger word filtering.
- Phase tracking: `getFullProgress()`, `getPendingPhaseTransition()`, `getPhaseProgressFraction()`.
- Many one-time flags: `hasSeenChallengeIntro`, `hasSeenDailyChallengeIntro`, `hasSeenJournalIntro`, etc.

### Weekly Quests (`weeklyQuests.ts`)

Two rotating quest tiers (seeded deterministic, local-day bucketing): **5 daily** quests + **5 weekly** quests (`loadWeeklyQuests` returns a `CombinedQuestState`). Types: solve_count, solve_difficulty, earn_stars, no_hints, challenge_mode, speed_wins, earn_amber, visit_animals, streak_days, sacrifice_amber (Phase 4+ only), tend_amber (Phase 5+ only), variant_wins (names an unlocked variant). Rewards: 6-30 amber base for dailies, 55-160 for weeklies, phase-scaled (1.0x → 2.0x). The sink quests (`sacrifice_amber`/`tend_amber`) are strictly **net-negative at every phase** they can appear (reward < required spend even after phase scaling) — pinned by an economy guard test in `weeklyQuests.test.ts`. **Generation context is persisted with the quest state**: the last context-FULL load's context (puzzlesSolved, phase, unlocks…) rides inside the stored state, so a context-LESS load after a period rollover (e.g. the header pill refreshing at midnight) regenerates from the persisted truth instead of an optimistic default — no more impossible cross-midnight quests. Quests stay **dormant until `JOURNAL_UNLOCK_PUZZLES` (6)** (`QUEST_GENERATION_MIN_PUZZLES`, the same gameBalance constant HomeScreen's light-mode gate uses): a pre-journal load stores a dormant placeholder that activates in place, same period, once a context-full load reports the gate crossed. On **full-moon event days** one extra `event_`-prefixed daily quest slot appears (`EVENT_QUEST_TARGET` 3 solves, `EVENT_QUEST_REWARD_AMBER` 20; title via `getEventQuestTitle`).

### Live Events (`liveEvents.ts`)

Serverless live-ops: every "live" event is **pure deterministic math on the player's LOCAL calendar** (no event server, no Math.random, no network — same date, same answer, every device). The one shipped event is the **full moon** ("the night the sky thins"): full moons are approximated from the 2000-01-06T18:14Z lunar epoch + the mean synodic month; a local day is an event day when it overlaps ±1.0 day of a full moon → a 2-3 day window roughly monthly (`isEventDay`/`getActiveEvent`; DST-safe via consecutive local midnights). Surfaces, all bonus-only: a 🌕 badge on the DailyChallengeCard, a **+50% daily-challenge amber bonus** (`getEventDailyBonusAmber`, credited via `awardBonusAmber(..., 'event_daily_bonus')` — never phase progress), one extra `event_` daily quest slot (see Weekly Quests), and a once-per-session home ambient moon line (`getEventAmbientLine`, `eventAmbientShownRef` in HomeScreen). All copy is phase-aware via `getEventName/getEventBadgeLabel/getEventAmbientLine/getEventDailyBonusLine/getEventQuestTitle` in phaseNarrative.

### Whisper Gallery (`whisperGallery.ts`)
Collectible archive of the lines that exist **nowhere else**: the post-victory whisper, the milestone offering response (`type: 'whisper'`), the answer a dialogue choice drew (`'choice'`), the Keeper's Record line (`'keepsake'`), and the late-pool line (`'passage'`, below). Cap: 500 entries. Phase-aware titles.

**It does NOT hold the base conversation corpus.** Phase-0..4 lines of `ALL_DIALOGUES` are owned by the journal's `Things We Kept` -> `Earlier conversations` (`services/storyArchive.ts`, which reads the corpus directly, so it is complete, ordered and un-evictable). `useDialogueFlow` used to copy every read line in here as `type: 'dialogue'`, which made the gallery a lossy second copy of the archive AND let the 500-entry cap evict the runtime lines that live only here. That producer is gated now; the legacy `'dialogue'` entries already on disk are KEPT (never purged) but hidden from every reader the screen uses via `HIDDEN_TYPES`/`visibleEntries`, and `getGalleryStats().totalCollected` counts the VISIBLE entries so the header can never advertise lines the list omits.

**The dividing line is what the JOURNAL CAN SHOW, not where a line was born.** `storyArchive` reads phases 0-4 of `ALL_DIALOGUES` and nothing else (`getStoryArchiveChapterLines` loops 0..4; `getStoryArchiveDialogues` returns `[]` at `phase >= 5`), so the three **late pools** the SAME dialogue-advance branch serves can never appear there: the Phase-2 exhaustion pool (`PHASE2_EXTRA_DIALOGUES`, a separate export), the post-revelation pool, and the ~65 Tending milestone lines (both assembled by `dialogue/phase5Pool.ts` from their own modules). Those ARE recorded, as `'passage'`, gated on `fromLatePool` in `useDialogueFlow` — a flag set by the very branches that already detect a pool line, so the two cannot disagree. Deleting the recorder wholesale (the first cut of this separation) silently retired ~455 lines from BOTH archives, the Tending Shrine's entire reward among them. `archiveSeparation.test.ts` pins the producer census and the gate; `dialogueFlowPagination.test.ts` pins the behaviour at the call site (a pool line is kept, a base line is not).

**Neither archive names a stretch of the story.** `getPhaseEraName` and the `PHASE_DESCRIPTIONS` era table it read (`Bright Days` / `Curious Thoughts` / ...) are DELETED, along with the gallery's per-entry era stamp (the card now shows its kind mark and the quote) and the journal's phase-indexed `STORY_COPY.archiveChapterTitles` (`By the warm hearth` / ...). An archive chapter is now ONE ANIMAL (`StoryArchiveChapter` = `{id, animal, count}`, `getStoryArchiveChapterLines` concatenates that animal's phase-0..available lines in order), so a chapter title is a speaker and its row body a count (`getStoryArchiveChapterSummary`) - a person and a number, never a mood. Do not reintroduce a table of names for the stretches of the story; `archiveSeparation.test.ts` guards both halves.

### The Offering / Sacrifice Mechanic (`sacrifice.ts`)
Phase 4+ **voluntary amber destruction** — the complicity beat. The amber is gone; the player gets **nothing mechanical** (never amber back, never phase progress — `updatePhase` is untouched). What it gives back is **recognition**, made richer in the "make it special" pass so the reward is pure flavor:
- **The altar stays OPEN** across repeated offerings (the modal no longer closes after each one — the #1 annoyance fix): the response renders inline ABOVE the still-tappable amount chips, the balance updates live, and a "Done" button ends the session.
- **In-session devotion streak**: consecutive offerings in one open session escalate the arrangement's response tone via `selectOfferingResponse({count, sessionStreak, phase, everything})` — calm → leaning → fervent (streak ≥3 / ≥6). Phase-aware pools: dread at Phase 4, serene at Phase 5. Milestones (2/3/5/10/25/50/100) still override and keep their contract keywords; the first offering keeps its "arrangement" welcome.
- **Devotion tiers** (`DEVOTION_TIERS`/`getDevotionTier`, cumulative-count standing, flavor only): Noticed(1) → Marked(3) → Known(8) → Kept(20) → Beloved of the Pattern(50) → One of the Arrangement(100). `performSacrifice` returns `tierUp` on the offering that crosses a threshold (metadata only — never replaces the response copy) so the altar can announce it.
- **The monument**: `getArrangementHoldsLine(total, phase)` + the current devotion title/regard render in the modal — watching the total climb IS the reward.
- **"Offer everything"**: a two-tap-confirm button gives the whole balance at once, with its own bespoke response pool (pays off the 100-milestone "You gave everything").
- **Felt feedback**: a candle flare (native-driven `sacrificePulse` scale + glow, reduced-motion aware) + `hapticMedium` on each offering.
- **Milestone offerings become Whisper Gallery collectibles** (`recordWhisper`, attributed to Ember, the flame-oracle).
- **One-time Phase-4 intro** (`getOfferingIntroLines` in phaseNarrative, `introContext: 'offering_intro'`): Ember, robed, formally invites the player into the rite (serene phase-5 variant). Gated by `hasSeenOfferingIntro`/`markOfferingIntroSeen` — the flag rides the already-synced `wordshift_sacrifices` state (so it follows the player across devices and clears on Reset All).

Preserve those coordinates when updating artwork rather than centering every glow or covering the resident.

### Notifications (`notifications.ts`)
Local push: daily reminders (phase-aware morning messages, scheduled as a ladder of non-repeating dated one-shots `DAILY_REMINDER_LOOKAHEAD_DAYS` (7) ahead, skipping today once the player has played — so a daily player never gets a redundant "puzzle is ready" ping. **Cadence caps (launch-readiness fix):** a NEW install (under `NEW_INSTALL_MAX_AGE_DAYS` 14 days OR under `NEW_INSTALL_MAX_SOLVES` 20 solves) arms mornings only on `NEW_INSTALL_REMINDER_DAY_OFFSETS` +1/+2/+3/+5/+7, never today, and the win-back rungs at +1/+3/+7 take precedence through the one-per-local-day dedupe, so a lapsed new player hears from the house on +2 and +5 mornings only (5 pings in the first week, not 7); a player whose play streak is `STREAK_COVERS_MORNING_REMINDER` (3) or more gets NO morning reminder at all while re-engagement pings are on, and instead the streak-risk ping arms for tomorrow 19:00 when today is already kept (with re-engagement off the morning ladder stays, since nothing else would cover them); while the Daily Challenge is still **locked**, the ladder still arms but with generic come-back copy routed **home** — never "your daily puzzle is ready" for content the player can't reach), streak-at-risk reminders (7pm the next missed day when streak ≥ 2, copy via `getStreakRiskMessage(phase, streak)`), an **escalating win-back ladder** for lapsed players (6pm one-shots at +1/+3/+7/+14/+30 days, `WIN_BACK_RUNG_OFFSETS` — 5 rungs; rung 1 shifts to the day after the streak-risk ping for streak holders; copy escalates via `getWinBackMessage(phase, rung)` in phaseNarrative, with special finished-story tail copy on +14/+30 for post-revelation players), and a **weekly-quest-expiry** reminder (Sunday **17:30**, deliberately staggered off the 18:00 win-back rungs so both can never land in the same minute, before the local-Monday quest reset; `getQuestExpiryMessage(phase)`, only when the player has weekly-quest progress in flight or unclaimed reward). Every notification carries `data.target` (`'daily' | 'home'`) so App can route the tap, and rides the named Android channel `reminders` ("Reminders", `REMINDER_CHANNEL_ID`, created by `ensureReminderChannel` before scheduling) instead of the default Miscellaneous channel. Each app session reschedules everything with the CURRENT phase — `setNotificationPrefs(prefs, currentPhase)` takes the phase too, so a Settings toggle never re-arms the ladder with bright Phase-0 copy; the streak/win-back/quest pings only fire on genuinely missed/relevant days. Phase 5 has its own quiet, watchful tone.

**Permission flow**: `scheduleAllNotifications()` never prompts — it only schedules when permission is already granted. The OS dialog is triggered solely by `requestNotificationPermission()`, reached two ways: the one-time contextual prompt after the player's 3rd+ victory (App.tsx `maybePromptForNotifications` → a styled in-game `NotificationPromptModal`, phase-aware + reduced-motion aware, NOT a bare OS `Alert`; copy from `getNotificationPromptText()`), or the Daily Reminders toggle in Settings. The prompt result is logged as a `notification_permission_result` event.

### Cloud Save (`cloudSave.ts`)
Client-side sync layer with a pluggable `CloudProvider` interface. A live Supabase provider activates when `supabaseUrl`/`supabaseAnonKey` are set in `app.json` → `extra` (**now configured**); it also powers the daily leaderboard + aggregate social proof. Falls back to `NoOpProvider` (no network I/O) when unconfigured. `collectLocalSaveData()` / `restoreFromCloudData()`. `SYNC_KEYS` lists the **actual** AsyncStorage keys each service writes (e.g. `wordshift_home_progress`, not `wordshift_progress`; includes `wordshift_daily_login`, `wordshift_cosmetics`, `wordshift_narrative_delivery`, `wordshift_daily_ladder`) — keep it in sync when adding a persisted key; `SYNC_KEY_PREFIXES` (`['wordshift_played_']`) prefix-syncs dynamic key families with no extra bookkeeping. Device-specific keys (`wordshift_device_id`/`install_id`/`wordshift_ad_pacing`), the local analytics buffer (`wordshift_event_log`), store-authoritative entitlements (`wordshift_entitlements`), the pending-IAP-grant ledger (`wordshift_pending_iap_grants`), and the sync-status meta key are intentionally excluded.

**Conflict guard**: the production Supabase adapter uses `upsert_save_v2` with the last acknowledged **server revision**, and reads with `get_save_v2`. A mismatched revision reports a conflict; a missing v2 capability fails unavailable rather than silently falling back to the old unconditional upsert. Settings → Backup & Restore offers explicit restore or keep-this-device choices, clearing the conflict only on success. Upload and manual restore share an operation queue; saved reset markers prevent a late pre-reset acknowledgement or automatic restore from resurrecting cleared progress. Boot uploads wait on the fresh-install restore. `remoteRevision` advances only on successful sync; device timestamps remain metadata and a fallback for custom providers, not the production overwrite authority. Recovery codes carry the secure owner capability and are shown only after a durable backup; never publish or log them.

**Read failures are failures (2026-09-22):** `loadChoiceState` (dialogueChoices) and the narrative-delivery `loadDeliveryState` no longer cache a default state when storage cannot be read or parsed (the next write would have overwritten every earlier answer, seed and callback); optional readers (the home badges, the dialogue hook's preload) catch instead. An onboarding step that is missing or unreadable for a player who has already solved puzzles resolves to `complete`, never back to the cold open.

**Mid-session restore cache hygiene**: every service with a module-level in-memory cache that is ALSO in `SYNC_KEYS` exports an `invalidate*Cache()`, and `invalidateRestoredServiceCaches()` (cloudSave) calls all of them, so a mid-session restore (Settings' "Use the newer save" or explicit recovery-code restore) can never leave a warm pre-restore cache whose next write silently overwrites the just-restored save. When you add a synced key backed by a cache, add its invalidator to that list.

**Backend security is RPC-based with RLS and a secure, unguessable cloud-owner capability. Knowing the recovery credential grants access to that save, so treat it as private. Production saves use the v2 conditional RPCs; the client must not downgrade to legacy save writes. Follow [Backend setup](docs/BACKEND_SETUP.md) for the current SQL/migration order and server validation. Source configuration alone does not prove that those SQL changes have been applied to the live Supabase project.

## Coding Conventions

- TypeScript with explicit types for props and state
- React Native StyleSheet (not inline styles)
- Functional components with hooks
- Import colors from `CandyColors` in `theme/colors.ts`; use `getPhaseTheme(phase)` for phase-aware
- **All player-facing text through `phaseNarrative.ts`** — never hardcode strings
- **Animation cleanup**: Store animation return values, `.stop()` in useEffect cleanup
- **Native driver preferred**: `useNativeDriver: true`; use opacity overlays instead of JS-bridge backgroundColor. As of the ship-readiness pass there are **zero `useNativeDriver: false` animations** in src/components — glows are pre-styled overlay Views with native-driven opacity
- **Never let a natively-animated view outlive its animation into a different layout.** On iOS Fabric, once NativeAnimated has driven a view's `transform`/`opacity`, that key is recorded in the view's `propKeysManagedByAnimated` set until the view is recycled (`prepareForRecycle`): React commits skip it (`RCTViewComponentView.updateProps`) and `RCTPropsAnimatedNode.restoreDefaultValues` is a no-op under Fabric, so a reused `Animated.View` that switches from a native-driven transform to a plain one keeps the last natively-set value forever (the Row DROP-row compaction bug). When two alternate subtrees key their children the same way, give the CONTAINERS distinct `key`s so the animated views unmount instead of being reused
- **Bevel label centring**: in `CandyButton`/`BevelRowButton` the label container's ONLY vertical inset is `paddingBottom: BTN_SHADOW_DP` (the baked cast-shadow row below the body); any `paddingTop` not mirrored below the shadow drops the label below the body centre (a `paddingTop: 10` once sat every Continue/price/Buy label ~5dp low). `TEXT_ROLE.label`'s lineHeight is fine to keep: RN centres glyphs inside a taller line box on both platforms (iOS compensates only while lineHeight >= the font's own line height, which 24 clears at every bevel size). Pinned by `bevelLabelCentering.test.ts`
- **Async-write affordances reveal late, never per action**: `StorySceneModal` shows its "saving" state (dimmed buttons + caption) only after a page write has been slow for `SAVING_REVEAL_MS` (350ms), with the caption on the page counter's own line; showing it for the few frames of an ordinary write read as the card flickering on every Continue. Double-tap protection stays on the `busy` ref, independent of what is shown. The card frame is also held stable within a scene (header art on every page of its scene, a reserved portrait slot on narrator/player pages of a scene where an animal speaks, the previous-page bevel occupying its slot invisibly from page one; the art is shown only when the card's available height clears `HEADER_ART_MIN_CARD_DP`, decided per scene, so small phones keep every action above the fold), because the centred content-sized card otherwise moved both edges by half of every mount/unmount. Pinned by `storySceneModalContracts.test.ts`
- **Device tier gating**: `shouldSimplifyAnimations()` to skip decorative animations on low-end
- **React.memo** on expensive pure components (e.g., Row)
- **MoveDelta pattern**: Undo uses lightweight deltas, not deep clones
- **Schema versioning**: `dataMigration.ts` for storage format changes
- **Concurrent spend guard**: `spendInProgress` flag in amberCurrency
- AsyncStorage with in-memory cache pattern (load → cache → return cached)
- TS strict: module-level nullable caches need local variable assignment
- `reducedMotion`: All animations must check and skip/set-instantly
- **Narrative consistency**: Any new feature must respect current phase. Cheerful-only-at-Phase-0.
- **No over-engineering**: Only make directly requested changes. Don't add features, refactoring, or docstrings beyond what's asked.
- Accessibility: `accessibilityLabel` and `accessibilityRole` on interactive elements; never convey information by color alone (see the ✓/✗ slot-preview prefixes); dark-phase text colors must hold ≥4.5:1 contrast against their backgrounds
- **No em dashes (—/–) in player-facing text** — dialogue, UI strings, alerts, accessibility labels. Use `...` for dramatic pauses, commas for asides, or split sentences (`noEmDashes.test.ts` guards this at runtime over the real content pools). **Straight quotes and apostrophes only** (no curly U+2018/2019/201C/201D): the same test's source sweep fails on a curly glyph in any string/template/JSX literal, with a shrink-only baseline (`CURLY_BASELINE`) for the few pre-existing chrome sites still owned elsewhere
- Store/legal: privacy policy, terms, and data-deletion pages are **live and publicly accessible** via GitHub Pages (served from `docs/`). Every other file in `docs/` is internal and must be listed in `docs/_config.yml`'s `exclude` by exact name: `docsSitePublication.test.ts` fails CI for any docs entry that is neither a public page, an asset those pages use, nor excluded, so a new internal doc cannot publish silently (internal reviews once served a defect list and story spoilers beside the privacy link). All three URLs are wired into `src/constants/links.ts` and surfaced in Settings → About (Privacy Policy / Terms of Service / Data Deletion rows); store-listing metadata in `docs/STORE_LISTING.md` points at the same live URLs

## Narrative Acceleration

Engaged players reach the Phase 4 reveal at the 90-puzzle floor (~day 11-12 at 8/day, finale ~day 15); an unaccelerated casual arrives near the weighted threshold (~124 — usually a little earlier, since ritual energy tops up weighted progress; ~day 45 at 2/day, post-revelation ~day 60). The `MIN_PUZZLES_FOR_PHASE` floors bind once weighted progress clears the thresholds ({1: 12, 2: 28, 3: 62, 4: 90, 5: 120} in gameBalance.ts):
- Three-star rate: a LINEAR ramp (no cliff) — 1.0x at/below `THREE_STAR_RAMP_START` (0.40), rising to the 1.5x ceiling at `THREE_STAR_RAMP_END` (0.60), so exactly 1.25x at a 0.50 rate; a one-point rate change no longer swings the reveal by weeks
- Long streaks (7+ days): 1.25x
- Hard difficulty: 1.5x
- Challenge mode: 1.5x (Blind Offering: 2.0x — the cap)

## Known Constraints

- `app.json` → `android.blockedPermissions` strips `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK` (expo-audio injects them; the game plays foreground SFX only, and shipping the typed FGS permission triggers Play's Android-14 foreground-service declaration for a capability the app doesn't have). Do NOT remove the block unless background audio actually ships
- **Bundled PNGs must be real, clean PNGs or the Android release build dies at `:app:mergeReleaseResources` with `AAPT: error: file failed to compile`.** Two guards: (1) `app.json` → `expo-build-properties` sets `android.enablePngCrunchInReleaseBuilds: false` so AAPT2 skips re-crunching the already-optimized art (the ~3.5MB skies + pit backgrounds otherwise stress the cruncher and cause non-deterministic collateral failures). (2) Art edited in phone/photo tools (Google Photos etc.) is exported as **JPEG bytes under a `.png` name** or with an embedded color profile (iCCP) — libpng inside AAPT2 rejects both. Run `node scripts/tools/sanitizePng.mjs <file.png>` (from `mobile/`) on any externally-edited image before committing: it decodes via jimp (PNG *or* JPEG) and re-encodes through pngjs to a minimal `IHDR/IDAT/IEND` RGBA PNG. JPEG also **drops the alpha channel** (flattens transparency to a solid color), so for art that needs transparency (the per-phase foundations), re-apply the original's alpha mask rather than shipping an opaque box
- Standard/reverse/double_shift/**speed** at ALL difficulties serve from pre-generated banks (lazy-loaded). **Speed reuses the STANDARD bank family** (`getBankForSelection` allows speed; `getBankKey` maps speed → `std_<diff>` / `lex_std_<diff>`) — a speed board is a standard board played against the clock, so it no longer generates on-device (the +1 extension stays gated to `variant === 'standard'`, so speed keeps its base size). **Zero-wait board serving:** with independent Standard, Reverse and Double Shift families including a dedicated Lexicon Reverse Expert bank, EVERY (variant × difficulty × lexicon) combination resolves to a pre-generated bank (with recycling), so the 30s on-device reverse path and the speed on-device path are both effectively dead. The only remaining on-device generation is intentionally-dynamic content: **echo puzzles** (every 5th Phase-3+ standard board, seeded from the player's own ritual words — a fast personalized forward-DFS with an instant bank fallback), and the **daily** (seeded/deterministic so every player gets the same board). Both are intentionally dynamic rather than combo gaps. The final board is now the instant authored CLOSED/CLOSER arrangement, with no on-device generation.
- On-device timeout: 2.5s standard, 25s reverse, 5s double-shift. Wrapper: 4s/30s
- Fallback pools: 60 pre-validated boards across EASY, MEDIUM, MEDIUM_PLUS and HARD (EXPERT reuses HARD when a fallback is needed)
- Dictionary: common English only (no proper nouns), 3-7 letters
- Arc layout uses `overflow: visible`
- Dialogue sessions persist across restarts
- House view: `react-native-gesture-handler` (vertical pan only). The pan is **native-driven**: the gesture writes `translationY` straight into `panRaw` via `Animated.event({useNativeDriver: true})` over an offset captured at BEGAN, and the rubber band is SAMPLED into the render interpolation rather than computed per frame in JS. Do not reintroduce a JS `onGestureEvent` that calls `setValue` — a per-frame JS hop plus style commit over this scene's ~30 animated children is what made the house scroll lag. The only per-frame JS left is the value listener that keeps `liveTranslateYRef`/`currentPanYRef` fresh (needed to capture a mid-spring base synchronously at BEGAN)
- TouchableOpacity in home components from `react-native-gesture-handler`; HomeScreen modals use react-native's
- Daily challenge uses Math.random override (concurrency-guarded)
- Victory flow: `isProcessingVictory` lock
- AnimatedBackground: opacity overlay (native driver compatible)
- Device tier detection reads installed RAM first ON ANDROID ONLY (`expo-device` `totalMemory` via a guarded literal require, a native module added 2026-09-14; at or below 3 GiB = 'low', never applied on iOS where 2-3 GB iPhones run the full set, which is what catches the 720x1600 / density-2.0 budget phones the pixel heuristic rated 'medium'), then falls back to the PixelRatio + screen-size heuristic; the result is cached once per process. `shouldPremountSpriteLayers()` (high tier only) gates the pre-mounted walk atlases and idle/talk layers in AnimalSprite; lower tiers mount them on first use and keep them
- **Current dependency health:** SDK 57 / React Native 0.86 replaces the SDK-56 Hermes version flagged for a memory regression. **Services (providers WIRED — live when configured, NoOp fallback):** As of the launch-prep pass, real provider adapters are registered in `App.tsx` and keys live in `app.json` → `expo.extra`, so the app ships with live IAP + ads when those keys are present; the NoOp providers remain the automatic fallback in Expo Go / when a key or SDK is absent.
- `services/entitlements.ts` — source of truth for owned items / Patron status (`isPatron()`/`isPatronSync()`, `grantEntitlements`, `setEntitlements`, `clearEntitlements`). AsyncStorage-backed, native-free.
- `services/iap.ts` — `BillingProvider` seam; holds `PRODUCT_IDS`/`purchaseProduct`/`restorePurchases`/`entitlementsForProduct` as pure code. **`services/providers/revenueCatBilling.ts`** (`createRevenueCatBillingProvider`) is the live RevenueCat adapter, registered via `setBillingProvider()` before `initIAP()`. Reads `revenueCatIosKey`/`revenueCatAndroidKey` from `extra`; products map to the `patron`/`adfree` entitlements. **`getProducts`/`purchase` MUST pass the CORRECT product category per SKU** — one-time/consumable products need `NON_SUBSCRIPTION`, the `supporter` subscription needs `SUBSCRIPTION`; a mismatch makes RevenueCat's Android fetch return `[]` and the Store reads "not available" (the NON_SUBSCRIPTION half was THE original launch blocker on the Play internal build; the subscription half was a revenue-pass regression fixed the same way). The adapter splits a mixed batch by `isSubscriptionProduct()` (`iap.ts`, source of truth = `SUBSCRIPTION_PRODUCT_IDS`), fetches each group with its own category (read off the loaded SDK's `PRODUCT_CATEGORY.*` with string fallbacks), and normalizes an Android subscription's `:basePlanId`-suffixed identifier back to the bare id (`revenueCatSubscription.test.ts`). `initialize()` also **silently restores entitlements**: it registers a customer-info update listener FIRST, then fetches `getCustomerInfo()` — a reinstall/new device gets its Patron/Remove-Ads back without the player finding the Restore button.
- `services/ads.ts` — `AdProvider` seam + ad policy as pure/testable code (`interstitialFrequency`, `shouldShowInterstitial`, rewarded daily cap, Patron suppression). **`services/providers/googleAdMobAds.ts`** (`createAdMobAdProvider`) is the live AdMob adapter, registered via `setAdProvider()` before `initAds()`; reads `admobInterstitialId*`/`admobRewardedId*` from `extra`. **GDPR/UMP consent is resolved strictly BEFORE SDK init and any preload** (single-flight gate; `initialize()` resolves immediately while the consent → init → preload chain runs in the background, so cold start never blocks on a consent form). `ads.ts` exposes `privacyOptionsRequired()`/`showPrivacyOptions()` — Settings → ABOUT shows a "Privacy Options" row only when required. AdMob app id is in the `react-native-google-mobile-ads` config plugin in `app.json`. **Interstitials are wired:** `App.tsx` calls `maybeShowVictoryInterstitial()` on the eligible next-level and home victory exits (`handleNextLevel`/`handleReturnHome`); the Collect Now/pit route is ad-exempt — exempting onboarding, the early window (`puzzlesSolved <= INTERSTITIAL_MIN_PUZZLES` (16) — v1.3.2 first widened it past the auto-collect window at 8 so the first interstitial never lands on the first mandatory-harvest sessions, then the pre-launch spacing fix raised 12→16: at 12 the first ad hit the exit of win 13, the SAME board whose start carries the one-time preview-graduation toast (`PREVIEW_GRADING_FULL_LIMIT`=12); at 16 the first ad lands on the exit of win 17, clear of graduation (board 13) and the challenge intro (15). The resulting early one-time-beat timeline: daily unlock 8 / mandatory first harvest 9 / reverse variant 10 / phase-1 pit ceremony 12 for engaged players / preview graduation 13 (immediately after an engaged player's first ceremony at 12, by owner decision) / challenge intro 15 / first exit nudge 16 / first ad on the exit of win 17. `EXIT_NUDGE_MIN_PUZZLES` is **16** (raised from 12, then 14, so the first share/patron alert can never land on the graduation board at 13 or the Challenge-intro win at 15); it now equals `INTERSTITIAL_MIN_PUZZLES`, which is fine because the nudge fires on the exit of win 16 and the first ad on the exit of win 17, and `runVictoryExitNudges` already skips when an interstitial showed, so they never stack on one exit), mandatory-harvest exits, pending phase transitions, queued final/post-revelation cinematics, and Phase 5 — so ads never interrupt a ceremony (incl. ward ignition) or the serene endgame. **The daily is exempt only from Phase 3 on** (`ads.isDailyInterstitialAllowed(phase)` — at the bright phases 0-2 the daily's reliably habitual session carries the normal interstitial cadence; from Phase 3 it's protected like the rest of the dread arc). `VictoryData.puzzlesSolved` feeds the cadence.

Android billing is configured; Android ads still intentionally use test units until the production cut. Native modules required for a real build: `react-native-purchases`, `react-native-google-mobile-ads`, `expo-tracking-transparency`. **Do NOT change these to `eval('require')` / a dynamic module string** — Metro only bundles a module it can see via a static `require('literal')`, so a dynamic require ships an empty bundle for the SDK and every purchase/ad silently no-ops on a real device (getProducts → [] → the Store reads "not available") even though it works in Jest/Expo Go. **The victory 2x counts claims, never offers.** `REWARDED_DOUBLE_DAILY_CAP` (5, `monetizationPrompts.ts`) is a cap on doubles the player actually TAKES per local day. The double adds the board's OWN amber, never its one-time windfalls (`getVictoryDoubleAmount` in `services/victoryDoubleAmount.ts`, shared by the claim and the victory screen; older receipts without the windfall fields double the whole amount). Presenting the slot records nothing: `canOfferRewardedDouble(phase)` is read-only, and the only writer is `recordRewardedDoubleClaimed()`, called from `useVictoryDouble` on a `status === 'claimed'` result (never on the idempotent `already_claimed` replay, and a failed record leaves the player with MORE offers than the cap, never fewer). An earlier build charged the cap on presentation, so a player who simply did not want the bonus spent all five by declining and the 2x vanished for the rest of the day without ever paying out - reported from the device as "it disappears after a few levels". The persisted counter was renamed `rewardedDoubleOffersToday` -> `rewardedDoubleClaimsToday` for that change: `load()` spreads the stored record over the defaults, so a day already spent on declined offers is freed by the update rather than at the next local midnight. **Known trade, accepted deliberately:** the slot now appears on every eligible win until claimed, which the presentation cap existed to avoid on the argument that an ever-present 2x makes the base reward read as the amount a rational player failed to claim; an affordance that hides itself when you decline it is worse, because the player cannot tell it from a bug. Phase 4+ suppression, the ad-free instant-double sharing the same slot and cap, and `ads.ts`'s own `REWARDED_DAILY_CAP` (8, already counting completed views only) are unchanged.

- **Pending-grant ledger (purchase recovery):** consumables and the starter pack save their final reward before returning success. `wordshift_pending_iap_grants` and `wordshift_applied_iap_grants` let recovery apply the reward and receipt without duplicating a previously delivered grant; these store-adjacent records are device-local and survive Reset All. Known successful payments retry their storage work without launching another native checkout. The RevenueCat adapter also saves `wordshift_iap_history_baseline` before checkout and reconciles eligible later transaction IDs, covering a kill before the immediate receipt was written. Historical transactions already present at that baseline are not blindly re-granted: they may have been spent. **Receipt matching (hardened 2026-09-22):** a RevenueCat receipt links to its checkout when its store time is within 1 s of Play's `purchaseDate`, or, failing that, when it is the ONLY receipt for that product new since the pre-checkout snapshot and dated within `RECEIPT_MATCH_WINDOW_MS` (2 minutes); an unlinked receipt matches the single nearest unlinked checkout in that window; a checkout receipt is stored even when `purchaseDate` is missing (device time). Each checkout takes at most one alias, so a genuine repeat purchase still credits. A malformed `wordshift_iap_checkout_receipts` is moved to `wordshift_iap_checkout_receipts_quarantine` (device-local) rather than trapping the player in a retry. This protects recoverable purchases in the same installation; it does **not** promise to reconstruct spent consumable balances across reinstall, account changes or loss of local history.
