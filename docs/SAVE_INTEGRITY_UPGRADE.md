# Save integrity upgrade

Reviewed against main `6f96ebb` on 2026-09-13. See [current build](CURRENT_BUILD.md),
[backend setup](BACKEND_SETUP.md) and [release gates](LAUNCH_CHECKLIST.md).

This change requires both the updated app and `supabase/save_integrity_v2.sql`,
applied after the original security setup. Nothing is deployed by editing these
files. **Applied state:** a read-only probe on 2026-09-14 found `get_save_v2`,
`upsert_save_v2` and `get_legacy_save_for_upgrade` deployed on the hosted project
and the legacy `get_save`/`get_save_timestamp`/`upsert_save` names revoked for
`anon` (commands and results in [backend setup](BACKEND_SETUP.md#hosted-state-verified-2026-09-14)).
The two-device conflict rehearsal against the hosted project and the later
[`rate_limits_v1.sql`](supabase/rate_limits_v1.sql) migration remain open.

The new WS2 code contains all 128 random bits generated by Expo Crypto. It is a
bearer credential: possession authorizes access to one backup. Do not place it in
logs, analytics or screenshots. A support identifier is a lookup reference and
must never by itself authorize deletion or restoration.

Existing local progress remains authoritative during upgrade. An old short owner
is retained locally for support, but is never used to silently import a shared or
colliding legacy row. A new strong owner receives this device's complete local
snapshot. Showing its code succeeds only after the new backup is durable. The
original legacy row is preserved for reviewed support recovery; this migration
does not delete or arbitrarily merge it. If only an old short code survives,
open/update the original device to generate a new code, or use a verified support
process. Already-overwritten remote data cannot necessarily be reconstructed.

The SQL revokes anonymous access to the weak legacy RPCs. Older app versions keep
local gameplay but cloud writes fail until upgraded. Coordinate backend rollout
with the native app release; Expo Crypto is a native dependency, so do not ship
this bundle to an incompatible OTA runtime. Do not roll back by re-enabling weak
RPCs. Preserve database snapshots and use a compatible app rollback.

Cloud writes require an acknowledged server revision. A missing/newer revision
produces a conflict; a network failure never permits legacy last-writer-wins.
Only the player's explicit overwrite choice bypasses revision matching. Device
timestamps describe the snapshot and do not authorize writes.

Local restore stages validated keys and migrations, then durably writes one
commit journal before replacing any keys. Bootstrap must recover that journal
before services read progress. An interrupted commit rolls forward; a failed
pre-commit stage leaves the old save intact. Never let a failed recovery boot the
game against a partially applied save. Keep a retry action that re-runs recovery.

Release verification: independent installs including same-clock installs;
immediate second-device restore after showing code; invalid/offline restore;
two simultaneous writers; clock skew; linked reset; rejected unknown/future keys;
failure/termination at every journal apply write; legacy local progress upgrade;
verified support handling for old-code-only devices; source-map and rollback check.

New Cycle commits its progress increment, inherited story archive and narrative
gate reset together. It uses ordinary revision checking when uploading; starting
a local cycle does not consent to replacing another device's newer save. Uploads
and manual restores share a queue through acknowledgement, and an old upload can
clear only the reset marker captured by its own snapshot.

The adapter coordinates participating service operations, not arbitrary JavaScript
async contexts. Critical UI actions are fenced during commits, and ambient Amber
and hint rewards enter their own queued transactions. Code added later must use
explicit transaction helpers only inside an owned transaction and cancel stale
session callbacks; cache invalidation alone is not cancellation.

Paid grants with a durable local intent apply currency and their receipt together.
The current RevenueCat adapter also reconciles completed native transaction IDs
newer than a durable installation history baseline, covering eligible payments
that never reached the JavaScript checkout result. Baseline receipts and applied
transaction IDs survive Reset All and stay out of cloud saves so old spent packs
cannot be replayed by restore. This is not a server purchase ledger or a guarantee
of consumable recovery after reinstall/account changes/provider-history gaps.
The first-Amber-pack bonus likewise has sticky local history. Native checkout,
reconciliation and actual process termination still require signed-device QA.

Progress now includes a durable `pendingCeremonies` queue. Phase confirmation and
its ceremony enqueue commit together; house completion is acknowledged after its
scene, and finale/post-arrival/New Cycle flows queue their required ceremonies.
Completion or deliberate confirmed Skip acknowledges the scene; an interrupted
scene replays from its beginning on restart. The queue does not retroactively
replay every historical ceremony for an old save. Creature introduction visits
and dialogue choices keep their own persisted progress and presentation ownership.

Victory double claims commit their completion receipt marker with the Amber
reward; Daily Amber and monthly Supporter claims similarly commit counters/markers
and currency together. Room/cosmetic purchases include spend, ownership and
automatic equipment in one transaction; tending includes spend and level. These
operations must keep using the transaction helpers when later features extend
saves. See [monetization integrity](MONETIZATION_SETUP.md#purchase-and-reward-integrity).
